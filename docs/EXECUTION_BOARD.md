# Fogell — Execution Board

Mission: **a faster and better Jenkins.** Near-100% compatibility is the goal;
`adr/0001` defines what "compatible" is permitted to mean, and `adr/0004`
forbids claiming it without a receipt.

Lineage: front end inspired by **Forge** (same Groovy-parser approach,
`adr/0002`); architecture and evidence discipline inspired by **McLoving**
(`adr/0007`, `adr/0008`). One primary language, F# (`adr/0006`).

## Operating contract

- Repository: private, HeMan `~/projects/fogell`.
- One coherent commit per ticket. No work on a dirty checkout.
- Every ticket states a falsifiable acceptance criterion. "Done" means the
  criterion was measured, not that code was written.
- Corpus manifest verified before any scoring run (`corpus/README.md`).
- No push, tag, release or publication without owner authorization.
- Imported Jenkinsfiles are untrusted. Parsing is unconditional; **execution is
  allowlisted by executed surface**, on a no-egress network, in a disposable
  workspace.
- Incomplete pattern matches fail the build (FS0025/FS0026).
- No scalar compatibility percentage is ever published.
- **Seal evidence LAST**, after the final review round. A bundle sealed mid-review attests
  to a snapshot that was never merged: FG-101's first seal recorded the pre-review
  implementation, and FG-104's omitted its own deliverable. The checksum makes a stale
  bundle look more trustworthy than no bundle at all.

### Batch composition (measured, not assumed)

Derived from 117 review findings across PRs #11–#17, counted rather than recalled:

| what the PR touched | review rounds |
|---|---:|
| leaf concerns — process groups, signals, one step (#11, #12) | **2** |
| the walker, `Fogell.Differential/Fogell.fs` (#13–#17) | **5–14** |

**55% of all review COMMENTS (76 of 138) landed in that one file.** (138 comments carry
117 distinct findings; the two counts are not interchangeable and are kept separate here.) Not because it
is badly written, but because it is where the cross-cutting invariants live, and every
new step rediscovers them one at a time.

Rules that follow from the numbers:

1. **A ticket that adds behaviour to the walker goes in its own PR.** Batching three of
   them multiplies rounds instead of amortising them: #13 carried three tickets and cost
   5 rounds, then spilled 9 unread findings into #14, which cost 14 more.
2. **Leaf tickets batch 3–5.** They did, at 2 rounds each.
3. **Measure Jenkins BEFORE writing the ticket's code.** Every ticket that began with a
   probe (FG-035, FG-045, FG-048b, FG-046) matched on the first or second receipt for the
   behaviour itself; every round beyond that came from invariants, not from Jenkins.
4. **A cross-cutting invariant is not a ticket line, it is a sweep with a test.** Fixing
   instances demonstrably does not stop recurrence — see the counts in Wave 3.5.

## Execution order (revised after 7 merged PRs)

The waves below are grouped by SUBSYSTEM, which is how the work was originally
conceived. Execution order is now different, because the measured cost of a ticket
turned out to depend on what it TOUCHES rather than which subsystem it belongs to.

    1.  Wave 3.5   invariants        one-time cost, removes a recurring one
    2.  Wave 3.6   harness capability unblocks 5 tickets incl. the largest one left
    3.  Wave 4     step coverage      now leaf work, batchable 3–5 per PR
    4.  Waves 5–8  as written

**Why invariants first.** 117 review findings across PRs #11–#17 cluster into five
cross-cutting classes (54 cancellation, 52 string/quoting, 40 abort-cause, 19
fail-closed, 17 narration). Each new step in the walker rediscovered them
independently — abort-cause was wrong six times, poll coverage five, narration five.
Fixing instances did not stop recurrence; three times the reviewer noticed the
repetition before I did. Wave 3.5 converts that into a one-time cost.

**Why harness second.** Five tickets are blocked on the same limitation — the harness
produces one build, of a plain job, on Linux, with no SCM. One of them is FG-052,
which a fresh count shows is the **largest remaining construct in the corpus** (49
files) and which the board had recorded as 15 and rated P2.

**What this reordering is not.** It does not add scope or reprioritise on taste. Every
number above is counted from the corpus or from review history, and the two
corrections it produced — FG-052's 3x undercount, and `docker`'s 70 raw hits being 13
real directives — are the kind of error that only shows up when you re-measure instead
of trusting the row.

## Wave 3.5 — Cross-cutting invariants (BEFORE more step coverage)

Every ticket here replaces a class of defect that has already recurred, with a **sweep and
a test**, not another instance fix. The counts are findings from PRs #11–#17 that mention
the class; they overlap, because one finding often touches two.

This wave exists because of a measured pattern: each new step added to the walker
rediscovered these invariants independently, and the reviewer noticed the repetition
before I did — three separate times. Ordering them ahead of Wave 4's remaining steps
converts that recurring cost into a one-time cost.

## Wave 6 — Security

| id | pri | status | item | acceptance |
|---|---|---|---|---|
| FG-070 | P0 | **DONE (re-scoped)** | Secret delivery: value bound as Jenkins binds it, plus a file companion | **Measured first:** a secret in the environment is readable from `/proc/<pid>/environ` by any process running as the same user, for the whole life of the step — which is what `withCredentials` does. Fogell writes the value to a **0600 file** and the environment carries only `<VAR>_FILE`. A test prints the child's own environ and asserts the value is absent. **CLAIM CORRECTED** after a Codex review on PR #11, which was right: this does **not** defeat the same-UID attacker the measurement identified. That process reads `<VAR>_FILE` from `/proc/<pid>/environ` and then simply opens the 0600 file, because it owns it too. What FG-070 actually buys: the secret is gone from the environment, so anything that dumps or logs `environ` (crash handlers, `ps e`, process explorers, child processes started before the binding) no longer captures it, and a **different**-UID reader is blocked. Protecting a secret from a same-UID process is not achievable on Linux without UID separation or namespaces — see FG-070b. **CORRECTED A SECOND TIME** by the FG-044 measurement: Jenkins' `withCredentials` binds the VALUE (`env \| grep -c '^TOKEN='` is 1, `${#TOKEN}` is the secret's length) and every real pipeline reads `$TOKEN`, so binding only a path breaks lift-and-shift for all 23 corpus files that use credentials. Fogell now binds the value for parity AND the `_FILE` companion; `Secrets.environmentForPathOnly` keeps the hardened form for a caller that accepts the incompatibility. What protects the value is **masking on every output path** (FG-071), not absence from the environment |
| FG-071 | P0 | **DONE** | Masking is defence-in-depth and **never silent** (`adr/0005` beat) | **Now genuinely wired to the output path.** A Codex review on PR #11 found the masker and detector were reachable only from their own tests — `Executor.runShell` forwarded `OnLine` and returned stdout/stderr untouched, so a step running `cat "$TOKEN_FILE"` streamed the literal secret while this row claimed masking was done. Masking now happens on the **streaming** path and the buffered stdout/stderr, and three tests fail if that wiring is removed. Masks the same forms Jenkins was measured to handle (literal, base64, case-folded), and uppercase hex was added to the detector after a Copilot review found only lowercase was generated. It does **not** mask reverse/hex/char-split — masking every encoding is impossible — but it **detects** them and names the encoding. That is the difference between a known gap and a silent one: Jenkins leaks these with the build green and no warning |

## Standing risks

1. **Acceptance ≠ compatibility.** 93.9% inherited acceptance against 0 proven
   receipts. FG-002 exists because of this and blocks the release lane.
2. **Interpreter sandbox.** ADR 0002 buys coverage and inherits Jenkins' script
   security problem. FG-013 and FG-072 are the mitigation and they are P0.
3. **Windows is claimed nowhere yet.** The hardware blocker is gone — a
   GitHub-hosted `windows-latest` runner is a real Windows host — but that
   changes only what is *testable*, not what is *proven*. A green Windows CI job
   licenses "Fogell runs on Windows" (FG-038a). Platform **parity** needs Jenkins
   producing receipts on that same runner (FG-038b). The charter must not promise
   parity until 038b has receipts, and a green 038a must never be reported as if
   it were 038b. Note also that Windows is demanded by **zero** of the 228 corpus
   files, so it earns no priority from the compatibility number.
4. **Untrusted corpus execution.** Parsing is safe; running is not. The
   allowlist-by-executed-surface rule is not optional.
5. **Non-durable numbers.** Forge's ~0 ms/step is the non-durable path. Any
   published latency must come from the durable path (FG-024).
