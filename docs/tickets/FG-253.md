# FG-253 — A stage or pipeline agent Jenkins cannot allocate (`label`, `docker`, `dockerfile`) is executed here on the built-in node as if it were `agent any`

Status: **TODO** (P2). Filed 2026-09-04 from the FG-247 tenure's reading of
`ljpengelen_jenkinsfile`; measured on Jenkins 2.568.1 and on this engine
before filing, not implemented.

## Measured, 2026-09-04

The lab has exactly one node, labelled `built-in`. A hand-written one-stage
probe job (not the corpus file; created, cancelled, stopped and deleted, queue
empty afterwards) with

```groovy
agent { dockerfile { filename "back-end/dockerfiles/ci/Dockerfile"; label "webapps" } }
```

and one step `sh "echo fg247-probe"` printed `[Pipeline] Start of Pipeline`
and `[Pipeline] node`, then sat at `building: true, result: null` with the
queue item's `why` reading `‘Jenkins’ doesn’t have label ‘webapps’`, polled
for five minutes; Jenkins never started the stage. `Fogell.Run.Host` on the
corpus file that shape came from ran the same stage on the built-in node and
printed `+ cd back-end`, `cd: can't cd to back-end`, `completed: failure`.

On this engine `AgentLabel`, `AgentDocker` and `AgentDockerfile`
(`src/Fogell.Ir/Pipeline.fs`) are parsed for admission; the differential's
execution preflight (`src/Fogell.Differential/Fogell.fs`) refuses only
`AgentUnmodelled`, and nothing in `Fogell.Execution` reads the agent kind.
A `label` the controller cannot satisfy, or a `docker`/`dockerfile` agent
whose image Jenkins would build or pull before the first step, is therefore
executed here as `agent any`: the divergence is silent and shaped like a
build that ran where Jenkins would have queued forever or failed on the
docker-workflow plugin.

## Sized

Thirteen admitted declarative corpus files carry such an agent at pipeline or
first-stage scope: eight by `label` (`Romeh_spring-boot-ignite`,
`Romeh_spring-boot-sample-app`, `TomCzHen_jenkins-android-sample`,
`jenkins-infra_pipeline-library`, `jenkins-zh_jenkins-cli`,
`msfidelis_jenkins-ecs-slaves`,
`murphysecurity_murphysec-jenkins-tools`, `ljpengelen_jenkinsfile`) and five by
`docker`/`dockerfile` (`Blazemeter_taurus`, `liatrio_pipeline-library`,
`maxyermayank_jenkins-pipeline-demo-api`,
`maxyermayank_jenkins-pipeline-demo-pwa`, `wanghaoxi3000_advproject`).
The list is FG-247's survey; it is not restated on the board.
`mjah_kubernetes-jenkins-cicd-pipeline-example` (stage agent `kubernetes`) and
`kitconcept_jenkins-pipeline-examples` (stage agent `node`) are NOT in the set:
the parser recognises only the direct `label` form as `AgentLabel` and sends
`node`, `kubernetes` and every other plugin agent through `AgentUnmodelled`,
which the preflight already refuses (Codex on #427 caught both mislabels in
the survey).

## Acceptance

Decide and implement one of the two, and seal it:

1. **Refuse at preflight, by name.** A `label` agent whose label is not one
   the engine offers, and any `docker`/`dockerfile` agent, is an execution
   refusal with a code that names the agent kind (`unsupported_agent` is the
   existing code for plugin-defined agents), at pipeline and at stage scope;
   the thirteen files stay `admitted` with the refusal named in the ledger.
2. **Model the label as a node requirement.** `AgentLabel` becomes a
   capability the scheduler must satisfy (FG-061 already filters claims by
   capability); a label no node offers queues rather than runs, and the
   differential compares Jenkins' `doesn’t have label` outcome against the
   engine's. `docker`/`dockerfile` stay refused until the docker-workflow
   plugin's image build/pull is modelled.

Either way: a receipt for a label the lab does offer (`built-in`) sealed
tier 1, and a case for a label it does not, whose Jenkins side is the queued
build's `why` text and whose engine side is the chosen refusal or queue
outcome.

## Not in scope

`agent { node { } }` and `kubernetes` (already `AgentUnmodelled`, refused);
the scripted `node('label') { }` form (scripted walker); `tools { }`
provisioning (FG-051).
