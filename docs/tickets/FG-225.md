# FG-225 — Controller trust-boundary architecture

Priority: **P1**
Status: **TODO**

## Why this is a design ticket

FG-224 reached a runnable single-node controller, but repeated review rounds
found local defects at the same two architectural seams: authority crossing
from the controller into build execution, and identity crossing between runtime
and maintenance database capabilities. The individual defects are closed in
FG-224. Continuing to add one more guard to that delivery ticket would obscure
the common design problem and turn publication into an unbounded review loop.

This ticket owns a deliberate design pass. It does not reopen FG-224 or block
merging its bounded single-node slice.

## Design questions

1. Define an authenticated, tenant-bound approval broker. Build code sharing the
   controller's OS identity must not be able to manufacture its own approval,
   and restart/replay must preserve prompt and decision identity without a raw
   writable filesystem inbox becoming authority.
2. Define one database startup state machine whose ordering and capability
   ownership are explicit: prove the runtime/maintenance pair, migrate, verify
   identities and least privilege, then bind. State what is guaranteed through
   direct PostgreSQL, session pooling, and transaction pooling.
3. Decide whether pair proof and migration must share a pinned maintenance
   connection or transaction to defend against active proxy rerouting, rather
   than only static configuration mistakes.
4. Replace scattered startup thunks and launch arguments with typed capability
   objects whose construction establishes the invariant their consumers need.
5. Specify observability and operator recovery for proof timeout, pool
   saturation, broker unavailability, migration refusal, and partial restart.

## Acceptance

- An ADR and threat model name principals, assets, trust transitions, replay
  rules, and fail-closed outcomes for approval and database startup.
- A sequence/state model covers fresh startup, migration, restart, approval,
  cancellation, and degraded dependencies without relying on review prose.
- A transaction-mode PgBouncer integration lane proves same-database aliases,
  different databases, concurrent probes, saturated-pool bounded refusal, and
  zero residual advisory locks. Direct PostgreSQL remains a control.
- The approval design proves that an admitted build cannot authorize itself,
  substitute another tenant/build/prompt decision, or replay a voided decision.
- Implementation is split into separately reviewable tickets with explicit
  migration/compatibility boundaries; no implementation work is implied by
  closing this design ticket alone.

## Boundary

This ticket does not add remote agents, mTLS transport, HA election, packaging,
or automatic replay of ambiguous external effects. Those remain independent
delivery dimensions.
