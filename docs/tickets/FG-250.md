# FG-250 — The scripted parser reads a lone `"` inside a `"""…"""` literal as the end of the string and silently parses the rest as more statements

Status: **TODO** (P2). Filed 2026-09-04 (committer's local clock) while
writing FG-248's executed case; measured on the FG-248 head, not
implemented. The Declarative lexer does not have this defect.

## Measured, 2026-09-04

`Fogell.Groovy.Parser.Parser.parse` on three sources (dumped with `dotnet
fsi` against the built assemblies):

```
echo """a "b" c"""      → [ echo(""); "a "; b(" c"); "" ]          (four statements)
sh """printf "%s" "[x]" | od -An -tx1"""
                        → [ sh(""); "printf " % s; " "[x]; " | od -An -tx1"; "" ]
def v = """a "b" c"""   → [ def v = ""; "a "; b(" c"); "" ]
```

Groovy reads each as ONE string; only three consecutive quotes close a
triple-double literal. Through `Fogell.Run.Host` a Declarative pipeline
whose `script { }` block holds the `echo` form reports `completed: failure`
with NO diagnostic and no output — the mis-parsed `echo ""` and the bare
expression statements run and one of them faults — and the `sh` form runs
`sh ""` after printing the step before it. The parser gives no refusal, so
this is the FG-016 shape (a rejection without a name or a position) on top
of a wrong parse.

Cause, read in `src/Fogell.Groovy.Parser/Parser.fs`: `gstring q` builds its
literal runs with `many1Satisfy (fun c -> … c <> q.[0] …)`, which stops at
ANY quote, and `between (skipString q) (skipString q) (many part)` then
fails on the first lone `"`; the enclosing `attempt` rewinds and
`gstring "\""` admits the leading `""` as an empty string. `tripleSingle`
does not share the defect: it uses `manyTill … (lookAhead (skipString
"'''"))`. The Declarative lexer's `tripleQuoted` uses the same `manyTill`
shape and is correct.

Corpus, measured with a regex over `"""…"""` spans and re-derived by the
pre-push verifier: 14 of 228 files carry a lone `"` inside a triple-double
literal, 29 literals in all; 13 of those literals sit INSIDE `script { }`
blocks (HariSekhon, MrRameshRajendran, SumitKr88 six times, VAD37,
aws-samples three times, cloudogu_gitops-playground), where the scripted
parser reads them. Eight of the 14 files are tier 3; seven for other
reasons named on their ledger rows (`environment`, `agent`, `input`, `post`
and parenthesised-argument refusals, and a `script { }` refusal at a GString
index key), and ONE — `cloudogu_gitops-playground` — for this defect: its
ledger refusal (`script block did not parse as Groovy: … 13:57: Expecting:
'}'`) is the mis-parse, and with the lone quotes inside that block's
triple-double literals escaped the block parses and the whole file is
admitted with four stages. So this is a measured corpus-admission lever of
one file, and reachable through any `script { }` or `when { expression }`
body and through a purely scripted Jenkinsfile.

Interaction with FG-248, found by the verifier: a mis-parsed literal can
put a slashy string in expression position, so `echo """a "b c""" + /x\d/
+ """d "e"""` (or the same inside `script { }`) was admitted with the wrong
AST on `origin/main` and is now refused naming `\d` inside a slashy — the
refusal is a symptom of this defect, not of FG-248's rule, and closing this
ticket removes it.

## What would close it

`gstring` for the triple form consumes a `"` that is not followed by two
more (the `manyTill … lookAhead` shape the other three consumers already
use), a parser test for the three sources above and for `""""` at the edge
(Groovy reads `""""x"""` as a string starting with a quote), a
differential case with a lone quote inside a `script { }` triple-double
`sh` body, and `cloudogu_gitops-playground` moving from tier 3 to admitted
in the regenerated ledger. FG-248's `script-letter-escapes` case escapes its quotes as `\"`
in the triple-double stage on purpose; once this closes, that comment
should say the escape is a choice, not a necessity.
