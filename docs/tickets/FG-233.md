## Acceptance (falsifiable)

1. Every container the hosted gate starts, execs into, stops, inspects or
   pulls goes through `FOGELL_CONTAINER_RUNTIME`, and the workflow sets it to
   `podman` at both of its switch sites. `rg -c '\bdocker\b'` over `gate.yml`,
   every `scripts/prove-*.sh` (including `prove-backup-restore-drill.sh`) and
   both drill scripts is zero outside the runtime switch itself, its refusal
   message, and registry image names such as `docker.io/...` — comments,
   `docker-stop.stderr`-style file names and fake-runtime shim paths all count
   and must be renamed or removed.
2. The hosted Postgres comes from `scripts/ci-postgres.sh start` in EVERY job that
   needs one — at `cee2c5a1` (after #320) that is `lane`, `controller`,
   `hang-proof` and `database`, each with its own `services:` block before this
   candidate because GitHub jobs cannot share a container — and no `services:`
   block survives: `rg -c '^\s+services:' .github/workflows/gate.yml` is zero. The
   lifecycle helper dispatches `"$runtime" run`, asks the runtime to allocate the
   loopback host port, reads that port back, and publishes the container, port,
   and test connection through `GITHUB_ENV`. That
   is a separate check from item 1 on purpose: a `services:` block contains no
   literal `docker`, so the word scan cannot see one. The drills still borrow
   exact-major `pg_dump`/`pg_restore` from the `database` job's container.
3. Every test and proof that used a service container passes under podman in
   its own job, not only the drills: the `lane` job's Store and database
   suites migrate and pass against the podman Postgres; the FG-232 inotify
   proof (`scripts/prove-fg232-controller-inotify.sh`, three direct
   `docker exec` calls and a `command -v docker` refusal at `c4b80f90`) passes
   through the switch; the FG-224 PID-1 proof and the FG-231 six-arm bounds
   harness pass on `ubuntu-latest` under podman with their measured budgets
   intact, and the FG-231 planted-hang arms still become named refusals under
   podman. (Codex, on the filing PR: the first cut named only the drills and
   FG-224/FG-231, so it could have been declared met with the Store suites and
   FG-232 unproven.)
4. The two drill scripts default to `docker` when run without the variable
   (`runtime="${FOGELL_CONTAINER_RUNTIME:-docker}"`); after this ticket the
   default is `podman`, so a bare local run of either drill uses the owner's
   runtime. (The local gate, `scripts/build-and-test.sh`, never runs the
   drills or the FG-224/FG-231 proofs — they are hosted-only — so it is not a
   measurement of this ticket and is not claimed as one.)

## Source candidate and local proof

The candidate makes `FOGELL_CONTAINER_RUNTIME: podman` a single global workflow
decision. The build matrix starts PostgreSQL only for its database-using lane;
the controller, hang-proof and database jobs each own another disposable
instance. `scripts/ci-postgres.sh` requests `127.0.0.1::5432`, reads the allocated
port from Podman, exports it to subsequent steps, waits for real readiness, and
guards cleanup by the `fogell-gate-postgres-*` namespace. Two simultaneous
instances on HeMan received ports 37231 and 32993, directly reproducing the
formerly impossible concurrent shape without collision.

Every controller operation now dispatches through `FOGELL_CONTAINER_RUNTIME`.
Rootless Podman needs `--userns keep-id` beside the existing numeric `--user` so
the least-privilege controller can write its bind-mounted scratch state. Its
ps-compatible `top -eo` runs *inside* the container and therefore reports
namespace PIDs, unlike the former runtime; the extinction proof now requests
Podman's explicit `hpid` descriptor and normalizes both supported runtimes to a
host-PID first column. This was observed failing first as a false surviving
Run.Host judgment, then passing with the corrected identity source.

Measured on HeMan with rootless Podman 4.9.3 and the digest-pinned SDK image:

- two concurrent PostgreSQL 16 starts selected distinct ports and both stopped;
- the FG-224 native and PID-1 controller proofs passed, including surviving-init
  controller-death cleanup, and FG-232 measured 0 watches / 0 instances;
- FG-231's six arms refused in 16, 12, 39, 44, 46 and 27 seconds and left no
  controller process or container;
- FG-085a killed 15 mutants and passed the live round trip; FG-081 refused four
  faults, killed four direct mutants and passed its live rehearsal; and
- the complete HeMan gate passed 1,036/1,036 project tests, all blocking proofs,
  287/287 receipt seals, FG-094's 228-file 200/200 accepted boundary, and tier-1
  1/1, against a fresh Podman PostgreSQL on dynamically allocated port 33777.

`scripts/prove-fg233-podman-gate.sh` is blocking in the audits lane. Its ten
mutants restore an Actions service block, restore fixed port 55440 in the hosted
helper, remove the explicit Podman selection, make cleanup run without an
exported container name, restore fixed-port fallbacks in `pg-test-db.sh` and
the two controller proofs, or sever the allocated-port readback from any of
those three consumers; each is rejected before the real workflow is accepted.
Hostile-runtime controls also require both controller proofs to refuse before
invoking an untrusted executable, and mismatched container/port controls refuse
before any database operation. The cleanup arm was added for Copilot's exact-head review finding: an
unconditional `always()` stop could add a confusing secondary failure after a
start that had not yet exported its state. Both lifecycle helpers arm cleanup
before `run`, so a runtime that creates a container and then returns nonzero
cannot strand it before export; the local helper also validates literal
container names and explicit ports. Hosted evidence is deliberately not claimed
until the exact candidate runs all four affected jobs on `ubuntu-latest`.
