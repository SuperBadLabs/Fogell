# FG-256 — The hosted gate took 34 minutes because one lane held four mutation proofs

Status: **IN PROGRESS** (P1). Depends on FG-255, which had to land first: the
`mutants` lane could not be reasoned about, let alone parallelised, while twenty of
FG-236's mutants were being judged against a residual mutation.

## Defect

The `gate` workflow is the only required check on every pull request and every push to
the default branch. Measured across the last 49 successful runs: **median 34.0 minutes**
(min 26.2, max 37.1). Queueing is not a factor — every job starts within 2–4 s.

The cost was not spread across the gate. On run `34046992371` (reproduced on
`34039005775` and `34014947145`):

| hang-proof | 4m 30s |

| controller | 2m 51s |

| lane (prelude) | 1m 59s |
| plan / gate | 6s / 4s |

The critical path was `plan (6s) → lane (build) (2109s) → gate (4s)`. Total machine time
was 56.8 job-minutes against 35.8 minutes of wall clock — a nine-wide fan-out returning
**1.59x**, because the second-longest job finished at 4m30s and eight runners then idled

**Four mutation proofs were 1810 s of 2103 s — 86% of the lane and 70% of the run.**
Each compiles and runs one hostile candidate per mutant; FG-236 alone does that 44 times.

`docs/CUSTODIAN_HANDOFF_2026-09-04_FG-236.md` had already recorded the 45-minute lane
timeout and refused any reduction "without first making the same blocking evidence
reliably faster". Moving it off the pull-request path is that.

## Fix — two tiers, one script

`scripts/build-and-test.sh` gains a `mutants` lane holding the four proofs, and declares
the tier split itself so neither workflow can drift from it:

```bash
GATE_LANES=(build audits prelude stale-refs lanes mutants)
GATE_SLOW_LANES=(mutants)
```

**Only the slow tier is listed; the fast tier is its complement.** An earlier draft
carried two lists and a check that they partitioned `GATE_LANES` — but that check would
then have been the only thing standing between a typo and a lane running in no hosted job
while every job stayed green. Deriving one side makes that state unrepresentable rather
than audited. `--list-lanes` takes `all|fast|slow`; bare `--list-lanes` still prints every
lane, because `scripts/bin/audit-gate-lanes` reads it to decide which lanes must own a
block, and narrowing the default would blind the partition audit rather than fail it.

`.github/workflows/gate.yml` asks for `--list-lanes fast` and drops its lane timeout from
45 to 20 minutes. `.github/workflows/gate-mutants.yml` runs the slow tier.

**An unset `FOGELL_GATE_LANES` still runs every lane and still prints a bare `OK`.** The
local HeMan gate is unchanged and remains the full one.

### Three constraints that shaped this

- **The `mutants` block sits below the first `build` block.** Every proof in it restores
  into `NUGET_PACKAGES`, and `prove-dependency-locks.sh` refuses a package cache that is
  not empty — that emptiness is part of what it proves. Placed above, the local `all`
  sequence would fail inside the lock proof, naming a cause unrelated to the edit.
- **`check-fg228-evidence.sh` stayed in `build`** even though its mutation proof moved. It
  runs the built Differential CLI with `--no-build` against the tree
  `prove-dependency-locks.sh` produced, and no such tree exists in a lane that builds
  nothing. It also asks a different question — committed probe digests against recomputed
  receipt seals.
- **The nightly starts PostgreSQL, for FG-251 alone.** Its proof runs
  `tests/Fogell.Controller.Api.Tests`, whose entry point prints `skipped: no PostgreSQL`
  and **returns 0** when no database answers. Without one the baseline would pass
  vacuously and every mutant would read as a survivor: a loud failure, but on every run
  and for the wrong reason. Grepping the four proof scripts for
  `FOGELL_TEST_DATABASE_URL` finds nothing — the dependency is in the test project they
  invoke, which is why this was nearly missed.

### `push`, not only `schedule`

A scheduled workflow only ever runs the **default branch's** copy of its file, and
`workflow_dispatch` is unavailable on a branch until the file exists on the default
branch. A nightly-only workflow therefore cannot be exercised before it is merged, and its
first real run would be the following night. `push: branches: [main]` makes the merge
itself the first run, and keeps a regression's blast radius to minutes rather than to the
next cron. Two facts are recorded in the file's header so a red nightly is not silently
ignored: GitHub disables scheduled workflows after 60 days without repository activity,
and a scheduled failure notifies only whoever last edited the cron.

No job in the new workflow is named `gate`. Branch protection requires exactly one
context and status contexts are matched by job name regardless of which workflow produced
them, so a second `gate` job would report into the required context.

## FG-233 had to grow with it

`scripts/prove-fg233-podman-gate.sh` hardcoded `.github/workflows/gate.yml`. A second
workflow — one that owns a PostgreSQL lifecycle — would have escaped every check in it:
free to declare an Actions `services:` block, name the unintended runtime, or leave a
cleanup unguarded, while the proof still passed and said it had checked the hosted gate.

It now discovers `.github/workflows/*.yml`, requires per file that starts, stops and
guarded stops all match, and requires a **named** cross-file total of five. The total is
named rather than derived because per-file balance alone accepts a lifecycle deleted
outright — zero starts and zero stops balance perfectly. Four planted arms were added on
the new workflow specifically, because the three existing workflow arms mutate `gate.yml`
and would all still pass if discovery silently skipped every other file:
`mutants-service-container`, `mutants-unguarded-stop`, `mutants-missing-runtime`, and
`deleted-lifecycle` — the last being the one that proves the cross-file total is
load-bearing.

## What this costs, stated rather than implied

A pull request no longer proves the four mutation proofs before merge. A regression they
would catch reaches the default branch and is caught by the merge run or that night's
cron, rather than before merge. `README.md` already holds that a green GitHub check is not
a substitute for the HeMan gate; this widens the distance between the two. The local gate
is unchanged and still runs all six lanes.

### No local wall-clock figures are quoted here

HeMan runs several agent sessions concurrently, and a `codex` session was executing its
own full `build-and-test.sh` (pid 2762015) throughout these runs. Every local timing taken
during this work is therefore contended and none is quoted as a measurement. The
20-minute and 60-minute timeouts are both justified from the **hosted** numbers on run
`34046992371` — 293 s of remaining build-lane work, and 1810 s of mutation proofs — which
is where the problem was measured in the first place.

### The two lanes, run locally

`FOGELL_GATE_LANES=mutants` runs exactly the four proofs and nothing else — no
dependency-lock proof, no test projects, no audits — and ends with the subset line rather
than a bare `OK`:

```
=== sdk ===
=== descriptor-bound API token-file mutation proof (FG-251, blocking) ===
FG-251 PROOF PASS: ...
FG-235 PROOF PASS: ...
FG-236 PROOF PASS: ...
FG-228 PROOF PASS: ...
OK (lanes: mutants — a subset, not the full gate)
```

`FOGELL_GATE_LANES=build` runs the lock proof, the eight Expecto projects and every
remaining blocking proof, and greps clean for all four moved proofs (`FG-251`, `FG-235`,
`FG-236`, `stash symlink containment`: zero occurrences each). `check-fg228-evidence.sh`
still runs there, as intended.

**One pre-existing failure, not caused by this change.** The build lane ends on HeMan
with:

```
FG-094 REGRESSION GATE REFUSED: corpus is present but the required external baseline
and Jenkins oracle are not configured
COMPATIBILITY REGRESSION OR SCORECARD CHECK FAILED
```

`scripts/check-compatibility-regression.py:381-387` refuses when the corpus is mounted
but `FOGELL_REGRESSION_BASELINE` / `FOGELL_JENKINS_ORACLE` are unset. Both the checker
and its invocation in `build-and-test.sh` are byte-identical to `origin/main`
(`git diff origin/main` touches neither), the refusal reproduces by running the checker
directly, and it is a property of this host rather than this branch. **It cannot occur in
CI**, where the corpus is not mounted and `build-and-test.sh` prints
`scorecard/regression check NOT RUN` instead. A HeMan run of the build lane needs those
two variables to complete.
