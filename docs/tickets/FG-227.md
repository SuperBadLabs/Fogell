# FG-227 — fflat vs running the `.fsx` under `dotnet fsi`

Status: **PARTIAL — PR #200's answer was invalidated; a retained, fail-closed
benchmark of the complete 32-core and 4-core paths remains**

## The question

FG-226 compiles eight `.fsx` sources to native binaries with fflat. The .NET
SDK is already a build dependency and includes `dotnet fsi`, so interpreting
the scripts might remove fflat's 929 MB store, version-only pin, brotli repair,
apphost-shim discovery, non-reproducible output, and one-maintainer supply-chain
boundary. That alternative was not measured before the compiled route landed.

Those costs are real. PR #200 attempted to show that amortized execution made
the compiled route about eleven times cheaper per gate. Review established that
the experiment did not support that conclusion.

## What the investigation established

The checked-in scripts cannot be run directly with a command such as:

```text
dotnet fsi scripts/fsx/audit-claims.fsx -- --strict
```

They define an `[<EntryPoint>]` `main`, but FSI does not invoke it. The command
prints FS2304, performs no audit, and exits zero. Any valid FSI comparison
therefore needs a retained runner or controlled source transformation that
invokes `main`, passes arguments exactly, and proves the audit actually ran.
PR #200 retained neither the runner nor its timing harness.

Invoking `main` under FSI also changes `Environment.ProcessPath` to the
`dotnet` host. The executable-relative root calculation then resolves under
`/usr`, not the repository. The observed outcomes are not one class:

- `audit-claims` scans zero source files and exits zero — a fail-open;
- `audit-board-numbers` refuses because the board and ledger are absent; and
- `generate-scorecard --check` refuses because its generated documents are
  absent.

An FSI route must derive the candidate root deliberately and retain falsifying
controls for both the zero-scan and wrong-root cases.

## Why PR #200's numbers are retracted

The proposed ticket and board row claimed 134 invocations, 21.53 s compiled
against 230.37 s interpreted, a 10.7× ratio, a 7.6-invocation break-even, a 4.1×
four-core floor, and a ≈ +39.7 s full net for FG-226. None is a publication
fact:

1. Wrapper instrumentation around `scripts/bin/audit-stale-refs` missed the
   mutated binaries compiled and executed under `$MUTANT_ROOT`.
2. It counted `generate-scorecard` once, although
   `prove-scorecard-receipt-mapping.sh` invokes its copied generator three
   times and the corpus-host compatibility lane invokes the production
   generator again.
3. The unretained FSI runner/source changes mean the claimed byte-identity and
   timing procedure cannot be reproduced from the branch.
4. The four-core estimate slowed shared audit execution but left the native
   compile fixed at the 32-core 12.57 s result. `build-audits.sh` uses
   `nproc / 3`; under a four-core affinity it compiles the eight tools
   sequentially, and the script records roughly 58 s for that path.
5. The ≈ +39.7 s net used an admitted, unrecovered −19.4 s savings term that
   conflicts with FG-226's only documented −21.85 s value. It is not a
   remeasurement.

Missing invocations may strengthen or weaken a ratio depending on which compile
and execution costs they add. They cannot be waved away merely because FSI has
startup overhead.

## What remains true

FG-226's compiled implementation is the current, proven production path. Its
source/equivalence proofs, authoritative gate, exact-head hosted gates, and
publication remain valid. This ticket does not reopen that implementation or
claim that FSI is better.

The accurate conclusion is narrower: **the mechanism choice has not been
compared reproducibly across the complete paths**. The old +8.42 s figure is a
subtotal over the rows printed in FG-226, not a full-gate net; the proposed
replacement is also unsupported. Both are labeled accordingly rather than
combined into a new headline.

## Acceptance for DONE

1. Commit a fail-closed benchmark harness that invokes each FSI `main`, passes
   arguments exactly, binds the intended repository root, and rejects a
   no-op/zero-scan run.
2. Before timing, prove exit-code and byte-output identity between native and
   FSI candidates over every measured fixture. Preserve deliberate ordering
   deviations as finding-set/multiset comparisons where FG-226 does.
3. Derive or trace the complete gate execution manifest, including production
   binaries, copied fixtures, all generator calls, and every temporary mutated
   checker. A planted omitted call must fail the accounting.
4. Measure the complete compile-plus-execution paths repeatedly on the quiet
   32-core host and under a four-core CPU affinity. Record raw samples,
   medians, affinity, tree, tool versions, and the exact command manifest.
5. Use only reproduced or immutable-source cost terms. If the babashka baseline
   cannot be recovered, publish no full FG-226 net.
6. Run the authoritative gate and obtain fresh exact-head hosted gates and
   Copilot/Codex coverage before moving this ticket to DONE.

## Nonclaims

- No current whole-gate ratio or four-core floor is established.
- `sync-scm-cases` remains outside live comparison because it pushes to the
  fixture remote.
- `probe-input` remains outside an engine timing comparison because its live
  path is dominated by Jenkins and polling latency.
- fflat's costs are not declared acceptable merely because it is the current
  proven implementation.
