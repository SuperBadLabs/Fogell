## Defect

The FG-229 runner's ANSI-decoration strip in `scripts/run-project-tests.sh`,

```
sed $'s/\033\\[[0-9;?]*[ -\\/]*[@-~]//g'
```

uses bracket-expression ranges (`[ -\/]`, `[@-~]`) whose members are defined by
the locale's collation order. Under `LC_ALL=C` they cover the intended ASCII
spans; under a collating UTF-8 locale (measured: `en_US.UTF-8`, GNU sed 4.9,
HeMan, 2026-09-01) the same ranges match nothing, the escape sequences survive
into the normalized log, the summary regex cannot match, and the runner refuses
every genuine Expecto success as "test project produced a non-success Expecto
summary". `scripts/prove-project-tests.sh` — and with it the whole
`scripts/build-and-test.sh` gate — therefore failed closed on pristine
`origin/main` in any UTF-8-locale shell:

```
./scripts/prove-project-tests.sh; echo $?   # rc=1 under LANG=en_US.UTF-8
LC_ALL=C ./scripts/prove-project-tests.sh   # rc=0
```

This is a false red rather than a false green, but it is the same board defect
as FG-229's inventory: a checker inheriting its behaviour from ambient context
instead of naming its target. The locale name alone does not even identify the
hazard — glibc's `C.UTF-8` collates by codepoint, so the ranges work there and
only a collating locale such as `en_US.UTF-8` exposes the defect.

## Implemented boundary

Every text tool on the summary boundary now names its locale. The
decoration-strip `sed`, the marker-counting `awk`, and the summary-extraction
`sed -E` run under `LC_ALL=C`, which both restores the C collation the ranges
were written against and makes the tools byte-oriented, so test output that is
not valid UTF-8 cannot make a pattern silently stop matching. The bash
`[[ =~ ]]` summary pattern cannot be locale-pinned per invocation, so its digit
ranges are replaced by enumerated bracket expressions (`[0123456789]`), which
have no collation at all. Only the checker's own tool invocations are pinned;
the test processes keep the caller's locale.

`scripts/prove-project-tests.sh` gains a locale arm that runs the runner under
explicitly named locales instead of whatever the proof inherited. It probes
`locale -a` for a UTF-8 locale whose collation actually diverges from C (the
range `[@-~]` failing to match plain ASCII), preferring it over a merely
UTF-8-named one; with the divergent locale it requires the runner to accept a
genuine ANSI-decorated success, accept a success whose summary line carries a
non-UTF-8 byte (which an unpinned extraction regex would refuse), and still
refuse failed and same-line-duplicate summaries so a mutant that skips
validation under UTF-8 cannot pass; a `LC_ALL=C` arm accepts the same success.
A host with no UTF-8 locale fails the proof with a named diagnostic rather than
passing silently; a host with only non-divergent UTF-8 locales says so on
stdout and runs the arm under one of them.

## Proof of failure

Measured on HeMan at the pre-fix source before the runner was touched:

- extended proof vs pre-fix runner, ambient `en_US.UTF-8`: rc=1;
- extended proof vs pre-fix runner, ambient `LC_ALL=C`: rc=1, refused by the
  new arm (`FAIL: genuine success was refused under en_AG.utf8` — the first
  divergently collating locale `locale -a` offered);
- single-pin mutants of the fixed runner: unpinning the strip `sed` and
  unpinning the extraction `sed -E` are each killed by a named arm.

Two mutants survive and are recorded rather than claimed: unpinning the
marker-counting `awk` (gawk's fixed-string `index()` is byte-safe under UTF-8
in practice) and restoring `[0-9]` ranges in the bash pattern (glibc's rational
ranges keep `[0-9]` ASCII-only). Both pins guard POSIX-undefined behaviour that
the measured glibc happens to get right; no available input distinguishes them
on this host.
