# FG-240 — The pipeline-level `timeout` argument check runs after the SCM checkout

Status: **TODO** (P3). Filed 2026-09-03 from the FG-123 round-4 pre-push
verifier's finding, reproduced on both engines before filing.

## Measured

Jenkins 2.568.1 (a transient job on the pinned lab, 2026-09-03, deleted
after the run), with

```groovy
pipeline {
    agent any
    options { timeout(time: 1, unit: 'NOPE') }
    stages {
        stage('one') { steps { sh 'touch stage-marker.txt' } }
    }
    post { always { sh 'touch post-marker.txt'; sh 'ls' } }
}
```

refuses the MODEL: `WorkflowScript: 3: Expecting "class
java.util.concurrent.TimeUnit" for parameter "unit" but got "NOPE" of type
class java.lang.String instead @ line 3, column 38.`, `Finished: FAILURE`,
and nothing runs — no `[Pipeline] Start`, no checkout stage, no marker.

Fogell at `origin/main` (`24262d76`): on a plain pipeline the refusal is
compile-shaped and nothing runs (FG-121 set `compileRejected` on this
branch). On a local SCM-defined pipeline (the FG-123 `FogellSide.runScm`
harness) the build first prints `Obtained Jenkinsfile from git …` and the
full clone narration (21 lines: `Cloning the remote Git repository`,
`> git init`, `> git fetch`, `> git checkout -f …`), leaves `Jenkinsfile`
and `.git` in the workspace, and only then refuses with disposition
`RefusedBeforeExecution`. The same shape FG-123's first cut had for
`ansiColor`, and the one FG-123 moved ahead of the SCM block.

A refused build's receipt compares disposition, result and the WORKSPACE
HASH (the omitted-output seal form). Jenkins' refusal leaves an empty
workspace; Fogell's holds the checked-out Jenkinsfile. An SCM case with an
unusable unit would therefore DIVERGE on the workspace hash. UNPROVEN by
receipt: SCM cases live in the fixture repository and none declares a bad
unit.

## Why

`deadlineFromOptions pipeline.Options` in `src/Fogell.Differential/Fogell.fs`
both validates the option (`WalkerRules.timeoutMs`, which returns `unknown
timeout unit '…'`) and emits the `Timeout set to expire in …` banner, and the
banner is MEASURED to print after the checkout (receipt
`checkout-scm-timeout-env`), so the whole call sits after the SCM block.
The validation rides along with the banner's placement.

## What would close it

Split the validation from the banner: run `WalkerRules.timeoutMs` over the
pipeline options beside the other compile-shaped option checks (before the
SCM block), refusing with `compileRejected` there, and leave
`deadlineFromOptions` where the banner belongs. Then a test on the SCM path
that the refusal precedes the checkout with empty output and an empty
workspace (FG-123's SCM test is the template), and the same for the plain
path. The `checkout-scm-timeout-env` receipt must still verify unchanged,
since the banner does not move.
