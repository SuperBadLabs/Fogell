# FG-094 — Exact-set compatibility regression gate

Status: **PARTIAL** — the checker, offline proof, and HeMan wiring are local. CI
has no corpus, external baseline, or Jenkins oracle, so live comparison remains
uncovered there. Review, publication, and owner adoption of a baseline remain.

## Contract

On a corpus host, `scripts/check-compatibility-regression.py` first runs
`scripts/bin/generate-scorecard --check`, then compares exact filename sets from
four independently bound inputs: the current corpus manifest, current ledger,
the baseline ledger read from the pinned historical Git commit, and the pinned
Jenkins oracle. `admitted` is accepted parse-only evidence, not ADR tier 2;
accepted means `tier == 1` or `tier == admitted`.

Let `BA`/`CA` be baseline/current accepted filenames, `BT`/`CT` baseline/current
tier-1 filenames, and `J+` the oracle's exact `reached_agent=True` filenames.
The gate passes exactly when:

```text
BT subset CT
(BA intersect J+) subset CA
```

Therefore gains and admitted-to-tier-1 promotions pass. An accepted loss is
allowed only when that pinned oracle says `reached_agent=False`. The proof's
synthetic `vinsguru_jenkins-pipeline.Jenkinsfile` row in `fixture/repo` is the
load-bearing compiled-but-not-reached allowed-loss control and proves that
`compiled` is not the decision oracle. The real pinned oracle independently
classifies `vinsguru_docker-selenium-jenkinsfile.Jenkinsfile` from
`vinsguru/docker-selenium-jenkinsfile` as compiled but not reached; that file
remains admitted in both live ledgers, and the live gate measured zero losses.
Counts are diagnostic only: equal-count swaps still fail, and every tier-1 loss
fails even in `J-`.

## Bound inputs and refusal boundary

The external baseline is a stable-read, nonsymlink regular JSON file no larger
than 16 KiB, outside the checkout, with duplicate keys refused and exactly the
ten documented keys. Types and lowercase full hashes are exact. Its commit must
be an ancestor of the candidate; its tree and historical ledger object must
match the declared hashes. Git calls discard inherited `GIT_*`, disable
replacement objects and system/global config, and use fixed safe configuration.

The oracle must be a stable-read external nonsymlink regular file with exact
SHA-256, CRLF records, the exact 16-column schema, strict booleans, unique
filenames, `reached_agent => compiled`, and pinned totals. Both ledgers and the
corpus manifest require exact schemas and unique names; ledger rows are sorted,
while the manifest's historically pinned byte order is canonicalized only for
the exact sorted-set comparison. All four inputs must declare the identical
filename set. Missing either external input on a corpus host refuses;
both variables are all-or-none. A host without the corpus reports an explicit
skip, so GitHub CI does not pretend to perform the live check.

## Evidence and limits

`scripts/prove-compatibility-regression.sh` builds an isolated historical Git
ledger and exact CRLF oracle. Its 43 outcomes cover the positive set rules,
equal-count swaps, `J+` and tier-1 losses, missing rows, baseline external-file
constraints, JSON/schema/suffix strictness, ancestor/tree/digest/set bindings,
oracle header/line-ending/boolean/implication rules, out-of-order unique and
duplicate manifest names, all-or-none environment,
scorecard-first ordering, hostile inherited Git state, and direct mutants for
counts-only, compiled-vs-reached, missing-row defaults, tier-1 omission,
replacement-object sanitization, suffix, and ledger schema checks.

This is an exact pinned-snapshot regression rule, not a semantic-correctness
proof, a general cross-version Jenkins claim, or a progress guarantee for files
already rejected in `J+`. It says only that previously accepted `J+` files and
tier-1 evidence were not lost under these exact inputs. Oracle creation,
baseline authority/authenticity, Jenkins/plugin/environment fidelity, corpus
provenance, CI live coverage, signatures, and protection from a hostile local
process changing files between stable reads are outside this ticket.
