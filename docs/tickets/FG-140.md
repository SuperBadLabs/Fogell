# FG-140 — An UNMATCHED `}` inside a slashy regex is refused

Status: **DONE** (P3). Fixed on 2026-08-18 by `711236bf` (FG-141, PR #98) and
never accounted; this accounting commit changes no code. Filed 2026-08-04
(`eafd7ab4`) as P1 from a measured `no_stages at 1:1`, repriced to P3 on
2026-08-05 (`de4de9e2`) when the symptom became a loud refusal and the corpus
count was measured as zero.

## The construction, as filed, and the fix that landed unaccounted

As filed: `balancedRaw` skipped `'…'`, `"…"`, `//` and `/* */` but NOT slashy
literals, so in

```groovy
when { expression { return 'ab' ==~ /a}b|ab/ } }
```

the `}` inside the regex was counted as a brace, the balanced region ended
early, and the whole pipeline structure was lost. After FG-143/FG-153 the
loss was reported as `malformed_syntax … opaque section` instead of a quiet
`no_stages`; the row said what remained was "`balancedRaw` counting depth
through a slashy span, which needs slashy-aware scanning".

That is exactly what FG-141 built. Signed commit `711236bf` ("FG-141: slashy
versus division, decided by position — at both scanner sites", 2026-08-18,
merged through PR #98 as `438f022a`) gave `Lexeme.balancedRaw` the shared
position rule `Lexeme.endsExpression`: after an expression end a `/` is
division, in operand position it opens a slashy span whose contents no
longer touch the depth count (`src/Fogell.Pipeline.Parser/Lexeme.fs`). The
same commit added the parser test "a when-expression's slashy does not end
the expression body" (`env.B ==~ /a}b/` inside `when { expression { } }`,
list `FG-141 slashy versus division`) and sealed receipt `when-slashy-brace`
— `'a}b' ==~ /a}b/` gating one stage and `'a}b' ==~ /nope/` skipping
another, tier-1 PROVEN on the pinned lab: the unmatched `}` this row filed,
in the construction this row named. The FG-141 row was flipped DONE; this
row was not — the FG-207/FG-123a/FG-203 shape, from a different branch.

## Re-measured, 2026-09-03

Dates in this ticket follow the repository's convention of the committer's
local clock (UTC−05:00), as the FG-239/FG-240 records do.

One transient pipeline job on the pinned Jenkins 2.568.1 lab (created and
deleted through the REST API) and the same Jenkinsfile through
`Fogell.Run.Host` at `origin/main` `2f2af43a`, four stages:

| stage | `when { expression { … } }` | Jenkins | Fogell |
|---|---|---|---|
| `filed` | `return 'ab' ==~ /a}b\|ab/` (the construction as filed, verbatim) | `filed-ran` | `filed-ran` |
| `def-slashy` | `def p = /}/; return 'x}' ==~ /x/ + p` | `def-ran` | `def-ran` |
| `paren` | `return 'ab' ==~ /a)b\|ab/` (an INVALID regex) | `PatternSyntaxException: Unmatched closing ')' near index 0`, FAILURE | `Stage "paren" skipped due to when conditional` |
| `after` | none | `skipped due to earlier failure(s)` | `after-ran` |

The two slashy-brace shapes — the filed construction and a slashy literal
bound to a variable inside the body — parse and run identically on both
engines. The third stage is not FG-140: the slashy PARSES on both engines
and the divergence is in evaluating an invalid pattern, which Jenkins
raises as a catchable `PatternSyntaxException` that fails the build while
Fogell's `=~`/`==~` arm folds every `Regex` construction failure (and its
100 ms backtracking timeout) into `false`. That is filed as FG-241 with
this probe as its measurement.
