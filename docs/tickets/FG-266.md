# `parameters { }` applied at admission, `params` read-only in scripts, submit envelope and `build_parameters` table

Priority: **P1**

Verb: **submit** a build with parameters and **read** them from the pipeline.

Status: **TODO**. Filed 2026-09-10 by the Track 4 re-cut (`adr/0009`).
FG-053b is MOVED here; its re-measure is the demand.

## Demand

The `parameters { }` and `params.` rows of [FG-263](FG-263.md)'s table
(FG-053b's re-measure read 18 for the block). Today the block is
parsed into `Pipeline.Parameters` and then dropped: no `params` binding and no
default injection. The one thing that does fire is the bracket-collection
preflight in `Fogell.fs`, which refuses a `choice(choices: [...])` declaration
as `unsupported_named_collection`, so a file with a `choice` parameter is
refused and a file with only `string`/`booleanParam` parameters runs with them
missing. A file reading `params.X` faults at `UnknownProperty` inside
`script { }` and gets no value at all in `sh` interpolation.

## Design

- **Domain.** `ParameterKind = StringParam | BooleanParam | ChoiceParam of choices | TextParam`;
  `password` and `credentials` kinds refuse (`unsupported_parameter_kind`)
  because they are secrets with delivery semantics FG-270 owns.
- **API.** `POST …/builds` accepts `Content-Type: application/json` with
  `{ "pipeline": "<source>", "parameters": { "NAME": "value" } }`; the raw
  `text/plain` body stays as today with an empty map. A submitted name not
  declared refuses `parameter_undeclared`. `Store.AdmitBuild`'s admission
  fingerprint includes the resolved parameter list so an idempotency-key
  replay with different parameters is the same 409 as a different source.
- **Store.** A new migration (next free number; 0015 at filing, since #424
  took 0012 to 0014) `build_parameters`: `(build_id, organization_id, name, value, source)`
  with `source IN ('declared_default','submitted')`, forced RLS with the
  `build_definitions` policy shape, immutability trigger, written in
  `AdmitBuild`'s transaction. `ExecutionClaim` carries the list.
- **Worker → Run.Host.** The worker writes `<attempt>-<fence>.params`
  (tab-separated, base64 values, the `credentialStoreFromSpec` wire
  discipline) beside the definition and passes `--parameters <path>`; never
  the environment, which is cleared on purpose. The journal records
  `ParametersDigest` beside `ScriptDigest`, so a resume with a different set
  refuses by name.
- **Walker.** `jenkinsProvided` (`Fogell.fs`) gains one env entry per
  parameter BELOW Declarative `environment { }`; the `script { }` environment
  gains `params` as a read-only `VMap` (`VStr` for string/choice/text, `VBool`
  for booleanParam); assignment to `params.X` refuses `params_immutable`. The
  bracket-collection refusal in `Fogell.fs` gets a descriptor-owned exemption
  for `choice(choices: [...])`, exactly as `rateLimitBuilds(throttle: [...])`
  has.
- **Harness.** `Jenkins.fs` submits the same parameter map to the pinned
  Jenkins (`buildWithParameters`), and the receipt's comparison contract names
  the submitted set.

## Acceptance

A tier-1 receipt for a corpus file declaring `parameters { }` and reading a
default via `params.X` in a `sh` body or `script { }`, once with defaults and
once with a submitted value, both engines agreeing on output and workspace
hash. Resume after SIGKILL with the same parameters continues; with different
parameters refuses by name.

## Jenkins probe first

Measure on luigi: the exact exception Jenkins raises on `params.X = 'y'`;
whether `params.X` and `env.X` agree for each kind; the console line Jenkins
prints for a `choice` default; and the ordering of parameter env entries
against `environment { }` when both define the same name.
