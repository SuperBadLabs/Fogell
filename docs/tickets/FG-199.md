# FG-199 — plan of correction

**Current behaviour is in `scripts/review-coverage.py`'s output, not here.** This file
states what is wrong, what will be done, and in what order. Numbers below are produced by
that script and must be re-derived rather than quoted from memory.

## The measurement

```
scripts/review-coverage.py            # exit 1 while any merged PR lacks coverage
```

On 2026-08-15: **45 of 60 merged PRs** merged a commit that at least one expected reviewer
never reviewed. Two distinct shapes, and the script names which applies per PR:

| shape | meaning | why it happens |
|---|---|---|
| `reviewed an earlier commit only` | the reviewer looked at commit A; commit B merged | the bots review on open; a push in answer to a finding is not re-reviewed |
| `never reviewed the PR at all` | the reviewer never submitted | it silently did not run, and nothing asked whether it had |

**THE SECOND SHAPE IS THE LOUD ONE AND THE FIRST IS THE DANGEROUS ONE.** A missing reviewer
is at least visible to anyone who looks at the PR page. A reviewer that approved an earlier
commit leaves a green, complete-looking PR whose landed code nobody read — and the commit
that differs is, systematically, the fix written fast under correction.

## Why it went unnoticed for 60 PRs

The pre-merge question was "are there unaddressed findings", whose empty answer is returned
equally by *no concerns* and *no reviewer*. Every mechanism that could have caught it
answers a subtly different question:

- a **check-run** attaches to the SHA reviewed, so querying the merge head shows absence
  even when the reviewer ran — this produced a false report that Copilot had stopped
- **`gh pr checks`** reports the gate, which is not a reviewer
- **`mergeStateStatus: CLEAN`** meant only "no *required* check failing", and until
  2026-08-15 nothing was required

## Plan of correction

Ordered by what stops the bleeding first. Steps 1-2 are cheap and prevent recurrence;
steps 3-4 address the backlog and are the expensive half.

1. **Stop the recurrence at the source — DONE 2026-08-15.** `main` is branch-protected with
   `gate` required. This does not address review coverage; it is listed because it removes
   the other way a bad commit lands, and because it was proven to block a red gate on PR #61.

2. **Make coverage checkable, then required.**
   - `scripts/review-coverage.py` exists and is proven to fail: exit 1 with an impossible
     reviewer, exit 0 with none required.
   - **NEXT**: a `--pr N` mode returning coverage for a single PR, so it can run pre-merge
     rather than only as an audit; then wire it into the pre-push verifier, which is where a
     human is already reading output.
   - Consider GitHub's own lever: *dismiss stale reviews on push*. It converts the dangerous
     shape into the loud one by invalidating a review when new commits arrive. It cannot be
     enabled without also requiring approvals, and **the bots COMMENT rather than APPROVE**,
     so enabling it as-is would block every merge. Decide deliberately; do not enable blind.

3. **Re-review the backlog.** 45 PRs is too many to re-open individually and the value is
   uneven: a docs-only board edit and a change to the walker do not carry the same risk.
   Triage by what the unreviewed commit TOUCHED, not by PR number —
   `src/Fogell.Differential/` and `src/Fogell.Groovy.Interpreter/` first, on the FG-002d
   evidence that 55% of all review findings landed in the walker.

4. **One ticket per unreviewed landed commit, for the tranche step 3 selects.** Filed
   against the commit, carrying the PR number, the merged SHA, the reviewed SHA and the
   diff between them — which is the only part that was never read.

## What this does NOT claim

- That any specific unreviewed commit is defective. Coverage is a process fact; no defect is
  asserted for any of the 45 without measuring it.
- That the pre-push verifier saw nothing. It runs an independent model review on every push
  and passed on each. The gap is GitHub-side review, and the two are not substitutes:
  the verifier reviews what is about to be pushed, and it is the same actor that wrote the
  code choosing when to run it.

## Acceptance

`scripts/review-coverage.py` exits 0 for every PR merged after the coverage check is wired
in, and the checker is proven to fail against a PR whose merge head carries no review. The
backlog tranche from step 3 is either re-reviewed or explicitly written off with a reason.
