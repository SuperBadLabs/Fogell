# FG-199 — plan of correction

**Current behaviour is in `scripts/review-coverage.py`'s output, not here.** This file
states what is wrong, what will be done, and in what order. Numbers below are produced by
that script and must be re-derived rather than quoted from memory.

## The measurement

```
scripts/review-coverage.py            # exit 1 while any merged PR lacks coverage
```

On 2026-08-15: **45 of 60 merged PRs** merged a commit that at least one expected reviewer
never reviewed. Two distinct shapes, and the script names which applies per PR:

| shape | meaning | why it happens |
|---|---|---|
| `reviewed an earlier commit only` | the reviewer looked at commit A; commit B merged | the bots review on open; a push in answer to a finding is not re-reviewed |
| `never reviewed the PR at all` | the reviewer never submitted | it silently did not run, and nothing asked whether it had |

**THE SECOND SHAPE IS THE LOUD ONE AND THE FIRST IS THE DANGEROUS ONE.** A missing reviewer
is at least visible to anyone who looks at the PR page. A reviewer that approved an earlier
commit leaves a green, complete-looking PR whose landed code nobody read — and the commit
that differs is, systematically, the fix written fast under correction.

## Why it went unnoticed for 60 PRs

The pre-merge question was "are there unaddressed findings", whose empty answer is returned
equally by *no concerns* and *no reviewer*. Every mechanism that could have caught it
answers a subtly different question:

- a **check-run** attaches to the SHA reviewed, so querying the merge head shows absence
  even when the reviewer ran — this produced a false report that Copilot had stopped
- **`gh pr checks`** reports the gate, which is not a reviewer
- **`mergeStateStatus: CLEAN`** meant only "no *required* check failing", and until
  2026-08-15 nothing was required

## Execution boundary

FG-199 is a **local pre-publication guard on HeMan**, even though the facts it
checks are GitHub review records. The command, its fixtures and its known-bad proof
run from `/home/srikanth/projects/fogell`; GitHub supplies metadata but does not
execute or vouch for the checker that judges that metadata.

That placement matters for the same reason the build gate belongs there: HeMan is
where the candidate commit, the local verifier and the rest of the pre-publication
evidence meet. A hosted job checking its own platform's review state would also run
too late to guard the act that publishes a replacement commit. The initial branch
may be published only after the ordinary HeMan gate; once a PR exists, FG-199 runs
locally at every review or merge boundary and refuses silent review absence or a
review attached only to an earlier head.

## Plan of correction

Ordered by what stops the bleeding first. Steps 1-2 are cheap and prevent recurrence;
steps 3-4 address the backlog and are the expensive half.

1. **Stop the recurrence at the source — DONE 2026-08-15.** `main` is branch-protected with
   `gate` required. This does not address review coverage; it is listed because it removes
   the other way a bad commit lands, and because it was proven to block a red gate on PR #61.

2. **Make coverage checkable, then required.**
   - `scripts/review-coverage.py` exists and is proven to fail: exit 1 with an impossible
     reviewer, exit 0 with none required.
   - **NEXT**: a `--pr N` mode returning coverage for a single PR, so the local
     HeMan guard can run pre-merge rather than only as an audit. It may query GitHub,
     but its decision and exit status belong to the HeMan pre-publication workflow.
   - Prove that mode on HeMan before trusting it: it must reject the recorded bad
     heads on PRs #58, #59 and #60 for the reviewer each one lacks, and it must
     reject an impossible reviewer while accepting an empty required-reviewer set.
     A proof that only runs after publication is evidence about the checker, not a
     guard on publication.
   - Consider GitHub's own lever: *dismiss stale reviews on push*. It converts the dangerous
     shape into the loud one by invalidating a review when new commits arrive. It cannot be
     enabled without also requiring approvals, and **the bots COMMENT rather than APPROVE**,
     so enabling it as-is would block every merge. Decide deliberately; do not enable blind.

3. **Re-review the backlog.** 45 PRs is too many to re-open individually and the value is
   uneven: a docs-only board edit and a change to the walker do not carry the same risk.
   Triage by what the unreviewed commit TOUCHED, not by PR number —
   `src/Fogell.Differential/` and `src/Fogell.Groovy.Interpreter/` first, on the FG-002d
   evidence that 55% of all review findings landed in the walker.

4. **One ticket per unreviewed landed commit — DONE 2026-08-15.** Triage split the 45 into
   **23 whose unreviewed diff touches engine source** and 22 that were docs or board only.
   Issues **#62-#84** carry one PR each, with the merged SHA, the last SHA any reviewer saw,
   the affected areas and the `git diff` that reproduces the unread change. Each states that
   NO DEFECT IS ASSERTED — the issue asks for the review that never happened, nothing more.

   **WRITTEN OFF, with the reason rather than silently:** PRs #13, #18, #19, #21, #26, #27,
   #28, #31, #32, #33, #37, #43, #44, #45, #50, #51, #52, #53, #54, #58, #59, #60. Their
   unreviewed diffs touch documentation, the board, or evidence files only. That is a
   judgement about BLAST RADIUS and not about correctness: a wrong sentence on the board has
   cost real rework this week, so "docs-only" means lower risk, not no risk. Re-run
   `scripts/review-coverage.py` to reproduce the split rather than trusting this list.

   The largest single gap is PR #24 at **110 unreviewed files**, which is where triage
   should start rather than at #62.

## Instance 46, recorded because the first 45 were not

**PR #61 — the PR that filed this ticket — merged uncovered, on 2026-08-15, knowingly.**
Codex reviewed the merged head `69f93fd`; Copilot's last review was `a62eecf`, so the final
commit (this file's triage record) landed unread by one expected reviewer. The gate was
green on the head and Codex had reviewed it, and the owner was told the PR violated its own
thesis before deciding to merge.

It is written here because the difference between this instance and the previous 45 is not
that it was avoided — it is that it was SEEN. A process that only records the violations it
manages to prevent will report itself healthy.

**AND IT EXPOSED A HOLE IN STEP 2 ABOVE.** Waiting did not help, and the missing review
CANNOT BE REQUESTED: `POST /pulls/61/requested_reviewers` for
`copilot-pull-request-reviewer` returns **422 — reviews may only be requested from
collaborators**, and the bot is not one. So the plan's assumption that an uncovered PR can
be sent back for review is FALSE for exactly the reviewers this repo relies on. Pushing a
new commit to re-trigger does not fix it either: that creates a new head which is itself
unreviewed, so the regress has no fixed point.

What that leaves, and step 2 should be re-planned around it: coverage can be MEASURED
before merging and the merge held by a human decision, but it cannot be REPAIRED on demand.
The lever is therefore to stop pushing after review — land the fix as a separate PR — rather
than to expect a re-review that no API can ask for.

## What this does NOT claim

- That any specific unreviewed commit is defective. Coverage is a process fact; no defect is
  asserted for any of the 45 without measuring it.
- That the pre-push verifier saw nothing. It runs an independent model review on every push
  and passed on each. The gap is GitHub-side review, and the two are not substitutes:
  the verifier reviews what is about to be pushed, and it is the same actor that wrote the
  code choosing when to run it.

## Acceptance

`scripts/review-coverage.py --pr N` is run from HeMan and exits 0 for every PR
merged after the coverage check is wired in. Its HeMan-side proof rejects the known-bad
review/head pairs on PRs #58, #59 and #60, rejects an impossible reviewer, and accepts an
empty required-reviewer set. The checker names the expected reviewer and the current head
SHA so absence cannot read as approval. The backlog tranche from step 3 is either
re-reviewed or explicitly written off with a reason.
