# Design pipeline-environment expression evaluation

Priority: **P1**

Status: **TODO**. FG-259 measured a reachable semantic difference before
allowlisting its corpus candidate: Jenkins evaluated a top-level zero-argument
helper used as an unquoted pipeline `environment` RHS, while Fogell retained the
call text. This ticket owns the missing capability; it does not authorize that
corpus file or claim compatibility.

## Measured boundary

The exact helper reads `env.GIT_BRANCH` and `env.BUILD_ID`, replaces `/` with
`.`, and concatenates the values. Two three-attempt controls on Jenkins 2.568.1
showed that it runs during pipeline environment setup and sees the pre-block
build environment: a late `withEnv` overlay cannot change the result, and
sibling `GIT_BRANCH`/`BUILD_ID` declarations are not visible to the helper.
Jenkins produced `null.1`; Fogell produced literal `getdockertag()`.

The current IR records only environment text plus literal/nonliteral
provenance. That cannot distinguish an unquoted Groovy expression from a
double-quoted GString. Environment resolution is also recomputed by consumers,
while Jenkins evaluates each RHS once per scope. Preamble functions currently
enter the Groovy interpreter only for hosted `script {}` bodies.

## Required design

Before implementation, specify and test:

- distinct literal, GString and expression provenance at pipeline and stage
  environment scopes without changing existing quote semantics;
- deterministic source-order, once-per-scope evaluation against the environment
  visible before that Declarative block, including Jenkins-provided values;
- top-level helper registration by name and arity for this phase;
- an effect-free environment evaluator: hosted steps, closures with effects,
  assignments outside the owned scope, non-scalar results and unsupported calls
  must fail closed before workspace effects;
- typed diagnostics and precedence for parse, lookup, arity, evaluation and
  coercion failures; and
- caching/lifetime rules for stage entry, retries, parallel branches and post
  conditions so a value is neither reevaluated nor leaked across scopes.

Acceptance requires direct Jenkins controls for missing and supplied ambient
branch values, slash replacement, build ID selection, eager timing, sibling
declaration invisibility and registry preservation. Focused tests and hostile
mutants must kill expression-as-GString, constant-return, lazy evaluation,
double evaluation, sibling/overlay leakage, step execution and unsupported
result coercion. Only then may a successor re-open the exact FG-259 candidate,
add its allowlist row, and run the fenced corpus lane.
