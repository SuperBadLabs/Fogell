# FG-210 — JUnit zero-result and allowEmptyResults contract

Status: **DONE** on 2026-08-22.

## Measured divergence

Pinned Jenkins 2.568.1 with JUnit plugin `1416.vd753e036de5e` treats a matched,
well-formed invocation containing no recognized result as terminal by default
and with explicit `allowEmptyResults: false`. Suite aggregate attributes do not
manufacture results, multiple zero-result files still produce one terminal
invocation, and `skipMarkingBuildUnstable` plus `skipMarkingStageUnstable` cannot
suppress it. The pinned diagnostic is
`None of the test reports contained any result`.

Literal `allowEmptyResults: true` changes that bounded outcome. For either a
matched zero-result aggregate or no matching report, Jenkins returns
`0,0,0,0`, exposes all four values as `java.lang.Integer`, continues, and
finishes SUCCESS. A permitted no-match invocation emits both
`No test report files were found. Configuration error?` and the aggregate-zero
notice. Without the option, no-match remains terminal. A zero-result report or
suite does not poison a sibling containing a recognized testcase.

Before FG-210, Fogell returned a successful zero summary for a matched
zero-result aggregate without requiring the option, and treated no-match as an
undifferentiated unreadable-report failure. This was the well-formed zero-result
ingest residual left open by FG-177 and bounded by FG-208 and FG-209.

## Implementation and retained proof

`Publish.parseJUnitWithAbort` distinguishes no matched reports from successfully
parsed inputs whose aggregate recognized count is zero. `Executor.runJUnit`
applies a typed `allowEmptyResults` decision only to those two conditions.
Default or explicit false returns terminal Failure with no test totals or stage
warning; true returns Success with exact `Some(0,0,0)` totals and no stage
warning. Existing malformed and zero-byte synthetic cases, genuine I/O faults,
checked-width errors, and interruption precedence remain unchanged.

The walker resolves absent, literal-false, and literal-true values before report
scanning through the same typed boundary as the two JUnit marking flags.
Rendered text, dynamic direct expressions, and duplicate binding remain
fail-closed rather than acquiring guessed coercion semantics.

Six tier-1 cases are retained and PROVEN:

- `fg210-junit-zero-result-default`
- `fg210-junit-zero-result-explicit-false`
- `fg210-junit-zero-result-allow-empty`
- `fg210-junit-no-match-default`
- `fg210-junit-no-match-allow-empty`
- `fg210-junit-zero-result-sibling`

The immutable completed evidence bundle is
`evidence/20260822T134946Z-fg210-junit-zero-result`.

Failure receipts compare terminal-reason presence rather than exact plugin
diagnostic wording. Focused Execution coverage holds the exact diagnostics;
the successful allow-empty rows compare their notices as ordinary ordered
output.

## Residual boundary

This slice does not claim arbitrary XML or namespace support. Unretained oracle
probes found that an arbitrary root with a direct testcase carrying `classname`
is counted, while the same shape without `classname` faults on the pinned
plugin. That wrapper/classname surface remains an FG-177 ingest residual.

The pinned plugin also has a distinct path when a script explicitly assigns
`currentBuild.result = 'FAILURE'` before `junit`. Fogell does not support that
assignment, and a failed non-failFast parallel sibling was measured not to be an
equivalent construction. That preexisting-explicit-result path remains
unsupported and unclaimed rather than inferred from ordinary branch failure.

JUnit duration, object/UI surface, numeric-width arithmetic, coercion beyond
exact typed/literal booleans, and other options also remain outside FG-210.
