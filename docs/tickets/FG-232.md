# FG-232 — The controller watched its working directory and exhausted the user's inotify budget

Status: **PARTIAL — implementation, proof, and gate wiring are complete;
exact-head hosted gate and review coverage are outstanding**

## Defect

`Fogell.Controller.Host` builds its host with `WebApplication.CreateBuilder()`.
ASP.NET Core's default content root is the current working directory, and to
reload `appsettings.json` on change the host's `PhysicalFileProvider` creates a
`FileSystemWatcher` over that root with subdirectories included, which on Linux
is one inotify watch per directory in the tree.

Observed on HeMan on 2026-09-02 at about 00:40 UTC: a controller (PID
1907597, started 00:37:04, cwd `/home/srikanth`, parent PID 1, binary under
`fogell-worktrees/qa-20260902-main-tip/src/Fogell.Controller.Host/bin/Release/net10.0/`)
held 65,361 inotify watches, counted with
`rg -c '^inotify wd:' /proc/1907597/fdinfo/*`, against the user limit
`fs.inotify.max_user_watches = 65536`. Every other `FileSystemWatcher` for the
user then failed: `tools/Fogell.Watch.Inbox` reported its Error event
(labelled OVERFLOW) and `scripts/prove-approval-watcher.sh` failed 3/3
standalone. `$HOME` on HeMan holds about 268,600 directories on one
filesystem, so the watcher hit the limit long before it finished the walk.

`rg -n 'FileSystemWatcher|inotify|PhysicalFileProvider' src/` finds nothing
in Fogell's own code; the watches are the runtime's.

## Mechanism, reproduced at small scale

The pre-fix Release build (`origin/main` at `5c567c83`) was started against a
scratch database in `fogell-fg060a` with the FG-224 environment, from two
directories, and its `/proc/<pid>/fdinfo` entries counted once `/health/live`
answered:

| started from | inotify instances | watches |
|---|---|---|
| a scratch tree of 150 subdirectories | 1 | 151 |
| an empty directory | 1 | 1 |

One watch per directory plus the root. The host logs the mechanism itself at
startup: `Content root path: <cwd>`. The 65,361 figure from `$HOME` was not
re-measured here: reproducing it holds the user's whole watch budget for the
run, which is the failure other sessions on the box were already paying for.

## Implemented boundary

`Program.hostOptions` builds the `WebApplicationOptions` the host is created
with:

- **`ContentRootPath = AppContext.BaseDirectory`.** The content root is the
  apphost's own directory, never the cwd. The explicit option is applied
  after the `DOTNET_`/`ASPNETCORE_` environment providers, so an ambient
  `ASPNETCORE_CONTENTROOT` or `DOTNET_CONTENTROOT` does not displace it
  (measured below). This also removes the cwd as an implicit configuration
  input: a controller started from `$HOME` no longer reads
  `$HOME/appsettings.json`, which is the FG-222 stance applied to the host's
  own inputs.
- **`Args = [| "--hostBuilder:reloadConfigOnChange=false" |]`.** The host's
  own reload switch, supplied as a host argument so no environment variable
  is needed. Every setting the controller acts on is read from its
  environment once by `ControllerConfig`, so nothing consumes a reload; with
  the watch off the host creates no `FileSystemWatcher` and holds no inotify
  instance. The process's real argv was never host input (`main _`) and
  stays ignored.

Measured on the same scratch database, each stage separately:

| build | started from | instances | watches |
|---|---|---|---|
| content root pinned only | 150-subdirectory tree | 1 | 14 |
| content root pinned only | the same tree, with `ASPNETCORE_CONTENTROOT` and `DOTNET_CONTENTROOT` naming it | 1 | 14 |
| content root pinned only | `$HOME` | 1 | 14 |
| both | 150-subdirectory tree | 0 | 0 |
| both | `$HOME`, with `ASPNETCORE_CONTENTROOT` naming the tree | 0 | 0 |

The 14 is the Release output directory: its 13 subdirectories plus the root.
It is bounded by the deploy layout rather than by the cwd, which is why the
reload switch is kept as well: with both, the count is zero whatever the
layout. Every run logged `Content root path:
.../src/Fogell.Controller.Host/bin/Release/net10.0/`.

`tests/Fogell.Controller.Api.Tests` (`FG-232 host content root and
configuration watch`) binds both settings: the options name the apphost
directory and carry exactly the reload switch, and a host built from them
reports that content root and carries `hostBuilder:reloadConfigOnChange =
false` in its configuration.

## Proof of failure

`scripts/prove-fg232-controller-inotify.sh` runs in the hosted `drills` job
after the PID-1 step, with the same PostgreSQL service, and locally against
`fogell-fg060a`. Its counter reads the process's `/proc/<pid>/fd` links,
counting each `anon_inode:inotify` descriptor as an instance whether or not
it holds a watch, and sums the `inotify wd:` lines of the matching `fdinfo`
entries; a count that cannot be taken (the process is gone, the table cannot
be listed or an entry read, or the table changed under each of five reads) is
a refusal that says `check unavailable`, never zero (FG-103 rule 2). The checker is shown to fail before it is trusted:

1. **`absent-process`** — the pid of a child the shell has already reaped.
   Expected: `FG-232 REFUSED: absent process: check unavailable:
   /proc/<pid>/fdinfo cannot be listed: No such file or directory`, status 1.
2. **`stand-in-at-bound`** — a Python process that holds exactly 64 inotify
   watches (one per fresh directory, via `inotify_add_watch`) and publishes
   its count only after the last is held. Expected: `stand-in at the bound
   holds 64 inotify watches across 1 instances; the bound is fewer than 64`,
   status 1.
3. **`stand-in-under-bound`** — the same with 63. Expected: a pass naming
   `63 inotify watches across 1 instances`, status 0, so the counter is
   proven to count and the bound to be strict.

Then the live arm: a scratch tree of 256 subdirectories (asserted with
`find`), a scratch database and role provisioned as FG-224 does (the first
controller run migrates and refuses with status 3, then the grants complete
the runtime capability), and the built controller started with that tree as
its cwd. The proof reads the controller's cwd back from `/proc` so the launch
cannot silently have happened from somewhere small, requires fewer than 64
watches, requires a clean exit on SIGTERM within the 15 s reap budget, and
then, with the log complete, requires it to name the apphost directory as the
content root and not the launch directory (the line is written on the console
logger's thread after the host has started, so it is read after exit rather
than raced). A controller that rooted at its cwd again would hold
257 and refuse. Every wait is bounded and named (FG-231), and the EXIT trap
reaps the stand-in and the controller and drops the scratch database.

Measured on HeMan against `fogell-fg060a` on 55445 with the Release build:
the proof passes in about 1 s, the controller holding `0 inotify watches
across 0 instances`, and leaves no controller process behind.

## The orphan, and whether the proofs can make one

The offending process was not the proofs'. Its state root was
`/sn8100/runs/fogell/worldly-7k-20260902/evidence/scratch/state`, its binary
a `qa-20260902-main-tip` worktree, its cwd `/home/srikanth`, and its
environment carried `_=/usr/bin/env`: a QA harness launch with `env`, still
running after its parent had gone. A second such controller (PID 2039065,
started 00:43:51 with the same state root) held 65,357 watches during this
investigation and exited on its own. Both FG-224 and FG-231 launch the tree's
own `bin/` path with state roots under `/tmp/fogell-fg224-proof.*`, which
neither process had.

Whether the proofs can orphan their own controller, by inspection and one
measurement:

- `scripts/prove-runnable-controller.sh` starts the native controller in the
  proof's own process group and reaps it from the body's last act and again
  from the EXIT trap (`release_controller`: SIGTERM, a 15 s bounded wait,
  then SIGKILL). Bash runs the EXIT trap on SIGTERM and SIGINT, so an
  interrupted proof still reaps.
- `scripts/prove-fg231-proof-bounds.sh` runs each mutated copy under
  `timeout -k 10 180`. GNU `timeout` signals the whole process group it
  creates, TERM and then KILL, so the copy's backgrounded controller receives
  both directly. Measured on HeMan: a backgrounded `sleep` under
  `timeout -k 2 1 bash -c 'sleep 300 & wait'` was gone after the bound, and
  one under `trap "" TERM` was gone after the KILL. The harness also refuses
  by name if a controller from this tree survives an arm.
- What remains is a SIGKILL of the proof shell alone from outside (an
  operator's `kill -9` of that one pid, not its group): no trap runs and the
  controller is orphaned to PID 1. That residual is unchanged and stated;
  with this fix its blast radius is a listener port and a scratch database,
  not the user's inotify budget.

## Acceptance

- The Release controller started from a 256-subdirectory tree, from `$HOME`,
  and with `ASPNETCORE_CONTENTROOT`/`DOTNET_CONTENTROOT` set holds no inotify
  instance and logs the apphost directory as its content root;
- `scripts/prove-fg232-controller-inotify.sh` exits 0 on HeMan, refuses each
  of its three planted arms by name, and exits nonzero with a named refusal
  when the bound is exceeded or the count cannot be taken;
- the `FG-232` unit test passes in `tests/Fogell.Controller.Api.Tests`;
- the FG-224 native proof and the FG-231 harness still pass on the fixed
  controller;
- the exact-head hosted gate passes with the FG-232 drills step green, and
  the exact head obtains Copilot and Codex coverage.

## Residuals and non-claims

- **The bound is a contract, not the measurement.** The controller measures
  zero; the proof refuses at 64 so that a future host component holding a
  handful of watches for a real reason is not a red gate, while a cwd-rooted
  watcher (one per directory) cannot pass from any launch directory the proof
  builds. A regression from zero to a few dozen would pass; the proof prints
  the count so it is visible in the log.
- **Only the controller is covered.** `Fogell.Run.Host` and the tools are
  not ASP.NET Core hosts and were not measured. The inbox watcher
  (`tools/Fogell.Watch.Inbox`) holds watches by design.
- **The 65,361 figure is the operator's observation**, reproduced at 150
  directories rather than at `$HOME` scale (see above).
- **The reload switch is a host configuration key, not an API.** It is the
  documented `hostBuilder:reloadConfigOnChange` setting the generic host reads
  from its host configuration; the unit test binds that a built host carries
  it, and the proof binds the effect (no inotify instance), so a runtime that
  stopped honouring it would fail the proof rather than pass silently.
