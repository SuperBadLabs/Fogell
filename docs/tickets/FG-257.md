## First lane refusal and guard fix

The first authoritative lane ran from signed evidence-control commit
`a89f892bd542478fcad8501df19655ce00970e99`. Both host access fences and
both no-egress fences were proven, the exact runtime tuple verified, and a
fresh random-ID Jenkins controller and home started. Before the target build
could run, the lane refused:

```text
Jenkins runtime guard refused: runtime-guarded corpus definition has 0 exact top-level stages anchors, expected one
```

The original injection helper recognized only the byte string
`\n  stages {\n`. FG-254's first runtime-backed case happened to indent that
section by two spaces; this file uses four. An evidence control had therefore
made one corpus author's formatting an undocumented execution prerequisite.
The lane promoted nothing, removed its disposable controller and home, and
removed both access fences.

The insertion point now comes from the same Declarative parser that admitted
the source. Its private parse result carries the exact source index immediately
after the top-level `stages {` opener; ordinary parse callers still receive the
unchanged `Pipeline` model. Guard injection inserts there, so indentation,
comments, strings, and nested `stages` spellings cannot select a second textual
anchor. The focused test covers both the original two-space form and a
four-space form containing a comment lookalike, requires exactly one marker,
and requires the guard to precede the first source stage.

The checker was proven to fail: restoring the exact two-space requirement made
the new four-space assertion fail with
`corpus formatting does not become a runtime-guard prerequisite`. The
unmutated focused test then passed.
