# `env.X = v` inside `script { }`, run-scoped and durable

Priority: **P1**

Verb: **set** an environment variable from a script and **read** it in a later stage.

Status: **TODO**. Filed 2026-09-10 by the Track 4 re-cut (`adr/0009`). Ships
alone: it is a walker rule.

## Demand

The `env.X =` assignment row of [FG-263](FG-263.md)'s table (the `script { }`
row is the population it lives in). Today the host refuses the
assignment and fails the build (`WalkerOrchestration.fs`, the `SetEnv` arm:
"the overlay does not cross the script boundary"). FG-178(b)'s
exclusion from the queue rests on this refusal and is retracted by this ticket
when it lands.

## Design

- `WalkerCtx` gains `SetBuildEnv: string -> string -> unit` and
  `BuildEnv: unit -> (string * string) list` under the existing output lock.
- Resolution order in `WalkerArgs` becomes: Jenkins-provided < parameters
  (FG-266) < build-env (script assignments) < pipeline `environment` < stage
  `environment` < `withEnv` and credential overlays. The relative position of
  build-env against Declarative `environment { }` is the one thing to probe
  before writing code.
- Durability: an assignment made by a finished step must survive that step
  being skipped on resume, or the resumed build is a class-A false success.
  New `Record.EnvAssigned of stage * stepIndex * name * value` in
  `src/Fogell.Journal/Records.fs`, written through `PersistenceHooks` before
  `StepFinished` (the `StepStageWarning` precedent), replayed by `Resume.plan`.

## Acceptance

A tier-1 receipt for a corpus file that assigns `env.X` in one stage's
`script { }` and reads it in a later stage's `sh`; a hand-written crash-lane
case proving the value survives SIGKILL between the two stages and resume.

## Jenkins probe first

Measure on luigi: whether a script assignment overrides a pipeline-level
`environment { }` binding of the same name in a later stage; whether it is
visible inside a `withEnv` in the same stage; and what `env.X = null` does.
