# FG-028 — forced tenant isolation

Status: **DONE locally; publication remains owner-controlled**.

Fogell's PostgreSQL tenant boundary is now enforced by the database. Migration
`0005_forced_tenant_rls.sql`, extended by FG-224's tenant-bearing definition,
enables and forces row-level security on all eleven
tenant-bearing tables. Every policy compares the row's organization with
`fogell_current_organization_id()`. With no setting the function returns NULL,
so no policy admits a row; malformed UUID context raises instead of widening
access.

`Store` opens a transaction for every organization-scoped operation and sets
`fogell.organization_id` with `set_config(..., true)` before any tenant query.
The final `true` is the load-bearing part: PostgreSQL clears the value at commit
or rollback, including when Npgsql returns the physical connection to its pool.
Explicit organization predicates remain as defence in depth and to keep tenant-
prefixed indexes useful, but correctness no longer depends on remembering them.

## Runtime and maintenance capabilities

The optional second `Store` connection string is the maintenance capability:

```fsharp
Store(runtimeConnectionString, maintenanceConnectionString)
```

`Migrate()` and the fleet-wide `ActivateRestore()` use that connection. All
tenant operations use the first connection. The one-string constructor remains
compatible for tests and single-role development, but production should not use
a superuser or `BYPASSRLS` role as its runtime connection.

A runtime role needs schema usage, DML on the eleven tenant tables, sequence usage,
and read access to `controller_metadata`. PostgreSQL also requires an UPDATE
privilege for `SELECT ... FOR SHARE`; grant that privilege only on the immutable
`singleton` column, never on `restore_epoch`:

```sql
GRANT USAGE ON SCHEMA public TO fogell_runtime;
GRANT SELECT, UPDATE(singleton) ON controller_metadata TO fogell_runtime;
GRANT SELECT ON organization_work_roots TO fogell_runtime;
GRANT SELECT, INSERT, UPDATE, DELETE ON
  organizations, projects, builds, nodes, attempts,
  events, outbox, log_chunks, effect_checkpoints, retry_decisions,
  build_definitions
TO fogell_runtime;
GRANT USAGE, SELECT ON ALL SEQUENCES IN SCHEMA public TO fogell_runtime;
```

The runtime role must be `NOSUPERUSER NOBYPASSRLS`. The maintenance role owns
or can migrate the schema and is kept out of request handling.

## Lineage closure

The migration also adds tenant-composite foreign keys from `events` to
`attempts` when `attempt_id` is present and from `log_chunks` to `attempts`.
Together with the existing composite keys, a child row cannot substitute an
attempt from another organization even when UUIDs are supplied directly.

## Acceptance proof

The live PostgreSQL test creates a real `NOSUPERUSER NOBYPASSRLS` role and
actually assumes it for the runtime connection. Through that role it creates
two complete tenant graphs using the production `Store` path, including build,
node, attempt, event, outbox, log, effect checkpoint, and retry decision rows.
It then proves:

- absent context returns zero rows from every tenant table;
- selected context returns rows for that organization and zero foreign rows;
- commit clears context on the same reused physical connection, with Npgsql's
  normal pool reset deliberately disabled so it cannot mask a session leak;
- malformed context fails with PostgreSQL UUID validation;
- a direct cross-tenant insert is rejected by `WITH CHECK`;
- all eleven tables have both `relrowsecurity` and `relforcerowsecurity` set;
- all eleven policies and both new composite foreign keys exist;
- mixed-tenant event and log attempt lineage is rejected by those keys;
- the runtime role cannot alter the restore epoch, while global restore succeeds
  through the separate maintenance connection.

The acceptance fixture was itself checked against three planted regressions on
fresh databases: disabled outbox RLS, a dropped log→attempt tenant FK, and a
session-scoped Store tenant setting. All three turned the suite red for their
named invariant; the unmodified control stayed green.

The migration source is SHA-256 pinned in the migration ledger test. Focused
development proof on a fresh HeMan database: **57/57 Store tests passed**.
The authoritative full-gate receipt and signed commit identity are recorded at
closure, not predicted here.

## Boundary

RLS constrains a database role to the organization selected by the controller's
authenticated request transaction. PostgreSQL custom settings are not an
identity provider: code already able to issue arbitrary SQL as the runtime role
can choose another organization setting. Preventing arbitrary SQL execution and
binding request identity to `OrganizationId` are controller/authentication
boundaries, not claims made by FG-028.
