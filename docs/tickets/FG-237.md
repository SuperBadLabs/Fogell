# FG-237 — Every lock file pinned FSharp.Core to the SDK's bundled library-pack hash, so locked restore failed on every machine that resolves it from nuget.org

Status: **PARTIAL** (P2). Fix on this branch; exact-head review coverage,
hosted gate, publication and merge remain. Filed 2026-09-02 from the grok QA
report's NU1403 finding, which the 2026-08-30 disposition (#240) had recorded
as "did not reproduce".

## What was measured (HeMan, 2026-09-02, tip `89776e3f`)

Every `packages.lock.json` in the repository (26 projects) carried the same
content hash for `FSharp.Core.10.1.301`:

```
FwQFuqOA1+qQnFl6Vqg6piS83ZRuKJqXJQxOM52M5tNarT2XQ/pMvw8fOOlnhcOYvdZyje2PJ8rK/J64ZI729Q==
```

`~/.nuget/packages/fsharp.core/10.1.301/.nupkg.metadata` on HeMan names where
that hash came from:

```json
{ "version": 2,
  "contentHash": "FwQFuq…",
  "source": "/usr/lib/dotnet/sdk/10.0.301/FSharp/library-packs" }
```

The F# SDK injects its `FSharp/library-packs` folder as an implicit package
source. The `FSharp.Core.10.1.301.nupkg` in that folder (3,051,664 bytes) is
not the nuget.org package (3,066,660 bytes), and NuGet's content hash of the
nuget.org package is

```
excLf2zM/qUB3WhRUfI0xvOOaPwcRAEdYT/BXe9eiTKySnWVuIKMQTf5+6ETy5nsb1dpLp1s2j2yAM/XcRgFMg==
```

So the lock restored only on a machine whose SDK ships a library-pack with the
first hash. Reproduction on HeMan itself, with the implicit source turned off
and a fresh package folder so nothing cached could satisfy the lock:

```bash
dotnet restore src/Fogell.Store/Fogell.Store.fsproj --locked-mode \
  --packages "$(mktemp -d)" -p:DisableImplicitLibraryPacksFolder=true
# error NU1403: Package content hash validation failed for FSharp.Core.10.1.301.
```

Why #240 concluded otherwise: its probe used an isolated cache and
`--no-cache`, which remove cached *packages*; they do not remove an implicit
*source*, and the library-pack is a source. The hosted gate is green against
the same lock (main run `33694896472`): its SDK resolved the same hash, and which
source served it there was not measured. The NU1403 that the 2026-08-30 and
2026-09-02 QA reports saw on Manyu was real: that SDK does not resolve the
package to the first hash, so it is the machine on which the lock was wrong.

## What closed it on this branch

- `Directory.Build.props` sets `DisableImplicitLibraryPacksFolder=true`, so
  every restore on every machine resolves FSharp.Core from the declared
  source (nuget.org) and records that package's hash.
- All 26 lock files regenerated with
  `dotnet restore Fogell.slnx -p:RestoreLockedMode=false --force-evaluate --packages <fresh dir>`.
  The diff is exactly the 26 `contentHash` lines for FSharp.Core; no other
  line of any lock moved.
- Verified: `dotnet restore Fogell.slnx --locked-mode --packages <fresh dir>`
  against nuget.org alone restores all projects with zero NU1403;
  `Fogell.Controller.Host` builds Release `--no-restore` from that graph.

## Transitional cost, and who pays it

A global packages folder that already holds the SDK-sourced copy (every
machine that restored Fogell before this change, HeMan included) keeps that
copy's metadata, and locked restore against the new lock fails NU1403 there
until the entry is evicted once:

```bash
rm -rf ~/.nuget/packages/fsharp.core/10.1.301
```

`scripts/build-and-test.sh` isolates `NUGET_PACKAGES` per lane, so the local
gate is unaffected. A developer's plain `dotnet build` needs the one-time
eviction. Until this merges, a checkout on the old locks and a checkout on the
new locks cannot share one global folder in locked mode: whichever restores
second re-populates the entry the other one needs. That window closes at
merge; the runbook records the eviction.

One latent trap stays: a restore that bypasses `Directory.Build.props`, or
passes `-p:DisableImplicitLibraryPacksFolder=false`, on an SDK that ships the
pack fails NU1403 against the new lock (measured on HeMan). No script in the
repository restores that way today; `prove-dependency-locks.sh` copies the
props into its snapshot and `fg037-controlled-dotnet.sh` copies the repo's.
