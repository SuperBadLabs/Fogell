# FG-203 — `def snap = env` hands out a SNAPSHOT of the map where Jenkins hands out a live object

Status: **PARTIAL — fixed on 2026-08-24 and never accounted; measured on both
engines and receipted a second time on 2026-09-03; exact-head hosted gate and
review coverage are outstanding** (P3). Raised by the pre-push verifier on the
FG-202 fix, from the code, unmeasured; filed at the reviewer's description per
the FG-193 precedent, "unclassifiable until a probe runs".

## The construction, as filed, and the fix that landed unaccounted

An `EVar` read of `env` yielded the cell's current map VALUE, and each wrapper
refresh REPLACED the env cell's map ref rather than mutating it, so
`withEnv(['A=one']) { snap = env }` then reading `snap.A` after the wrapper
exited kept reading `one` here, where Jenkins' `EnvActionImpl` reference reads
the RESTORED environment. That was REAL from FG-193 (2026-08-17) until
2026-08-24.

Signed commit `fce392c4` ("FG-203 preserve live env aliases", 2026-08-24)
fixed it in `src/Fogell.Groovy.Interpreter/Interpreter.fs`: a wrapper refresh
now mutates every registered Jenkins env map IN PLACE
(`refreshJenkinsEnvMaps`), so an alias and the `env` cell keep sharing one map
ref and every read through the alias sees the live environment. It added the
case and receipt `script-env-alias-restoration` (tier-1 PROVEN: aliases taken
before and inside nested wrappers, read across return and fault exits) and the
unit test list `FG-203 live hosted env aliases`, whose comment states the
mechanism ("replacing the VMap behind the owned `env` cell leaves every
previously captured alias pointing at a stale snapshot"). The commit reached
`main` inside PR #148 (FG-224, merged 2026-08-27T03:55Z as `20d4b638`), the
scorecard was regenerated in `84354e21`, and this row was never flipped — the
same shape as FG-207 and FG-123a, carried by the same branch. This ticket
accounts it, and adds the filed construction verbatim as a second receipt.

## Measured, 2026-09-03

Two transient pipeline jobs on the pinned Jenkins 2.568.1 lab (created and
deleted through the REST API; the values below are not reproducible from the
repository beyond the sealed receipt) and the same Jenkinsfiles through
`Fogell.Run.Host` at `origin/main` (`46c40c1c`):

| shape | Jenkins | Fogell |
|---|---|---|
| alias taken INSIDE `withEnv(['A=one'])`, read inside | `inside=one` | `inside=one` |
| the same alias read AFTER the wrapper exits | `after=null` | `after=null` |
| `env.A` read after the wrapper | `direct=null` | `direct=null` |
| alias taken OUTSIDE, read inside `withEnv(['B=two'])` | `outer-alias-inside=two` | `outer-alias-inside=two` |
| that alias read after the wrapper | `outer-alias-after=null` | `outer-alias-after=null` |
| WRITE through the alias inside a wrapper, `snap.C = 'three'` | `inside-c=three`, `after-c=three alias-c=three`, SUCCESS | refused (below) |
| the same write spelled directly, `env.C = 'three'` | not measured here | the same refusal, byte for byte |

On every READ the alias follows the live environment exactly as Jenkins'
reference does. The one divergence is a WRITE through the alias, and Fogell's
journal carries the identical `step-reason` for the alias and the direct
spelling:

```text
script block assigns `env.C`; Jenkins applies that to every later step, and Fogell's environment overlay does not yet cross the script boundary. Refusing rather than accepting an assignment that does nothing
```

That is FG-178's deliberate fail-closed boundary — the live-queue prose
records that FG-178(b)'s wrong answer "stays unreachable while the host
refuses `env` assignment inside a script" — and nothing about it is
alias-specific.

## Closure

Receipt `script-env-alias-after-wrapper` seals the five read shapes tier-1
PROVEN on the pinned lab (same result, same output, same workspace hash),
beside the 2026-08-24 receipt; 294 receipt seals verify and the generated
scorecard moves from 292 of 292 to 293 of 293 expected cases. No code changes
in this commit. The write shape is not added as a case: it diverges by design
until FG-178 lands, as FG-126's and FG-239's probes are kept out of
`differential/cases/`.

## Residuals and non-claims

- The new case's post-exit reads are all `null`, which refutes the snapshot
  (a snapshot prints `one`) but cannot by itself distinguish a live alias
  from a detached empty one; `script-env-alias-restoration` is the stronger
  witness (an inside-taken alias reading a non-null outer value after the
  inner wrapper exits).
- `snap['A']` reads live; `snap.getAt('A')` and `snap.is(env)` are refused by
  name as non-builtin calls (fail-closed, Jenkins unmeasured). A script-level
  `def` declared before `pipeline { }` is not visible inside a later
  `script { }` block here (`UnknownProperty`), where Jenkins closures capture
  it — fail-closed, unmeasured on Jenkins, adjacent to FG-188 and outside
  this ticket.
- A write through an alias, or directly, inside a `script { }` block remains
  REFUSED by name; Jenkins runs it and the assignment persists after the
  wrapper. That is FG-178's boundary.
- Aliases of `env` handed across hosted wrapper bodies other than `withEnv`
  are covered only as far as `script-env-alias-restoration` reaches.
