# FG-070 — Secret delivery: value bound as Jenkins binds it, plus a file companion

**Status:** **DONE (re-scoped)**  ·  **Priority:** P0

Archived from the execution board on 2026-08-02. The board carries the
outcome; this file carries the reasoning, which is what a future reader
needs and what a planning table cannot hold.

---

**Measured first:** a secret in the environment is readable from `/proc/<pid>/environ` by any process running as the same user, for the whole life of the step — which is what `withCredentials` does. FG-070 initially put the value in a **0600 file** and carried only `<VAR>_FILE`; a test printed the child's own environ and asserted the value was absent. **CLAIM CORRECTED** after a Codex review on PR #11, which was right: that path-only design did **not** defeat the same-UID attacker the measurement identified. Such a process reads `<VAR>_FILE` from `/proc/<pid>/environ` and then opens the 0600 file, because it owns it too. The optional path-only form avoids environment capture and blocks a **different** UID, but same-UID protection requires UID separation or namespaces — see FG-070b. **CORRECTED A SECOND TIME** by the FG-044 measurement: Jenkins' `withCredentials` binds the VALUE (`env \| grep -c '^TOKEN='` is 1, `${#TOKEN}` is the secret's length) and every real pipeline reads `$TOKEN`, so path-only binding breaks lift-and-shift for all 23 corpus files that use credentials. Fogell now binds the value for parity AND the `_FILE` companion; `Secrets.environmentForPathOnly` retains the incompatible optional form. What protects the default value is **masking on every output path** (FG-071), not absence from the environment

## FG-073 threat-model audit closure (2026-08-27)

The current-tree threat-model review found a narrower implementation defect in
the different-UID claim: `WriteAllText`/`WriteAllBytes` created a secret file
under the process umask and only then changed it to mode 0600. With a traversable
parent and permissive umask, another UID had a read window before the chmod.
Text and binary companions now use `CreateNew` with owner-read/write mode on the
opening syscall, then restore exact 0600 through the open descriptor before any
secret byte is written because the process umask may remove owner bits. The
execution suite observes the empty pre-write boundary and checks both text/binary
content plus a restrictive-umask subprocess. Catchable failures inside a bound
body now revoke through `finally`; a separate construction catch revokes an
already-created sibling when a later binding fails. Differential regressions make
both cleanup arms load-bearing. Abrupt process death and failed best-effort
deletion can still leave owner-only files in the controller `_secrets` tree;
there is no startup reconciliation yet. These changes close the pre-chmod and
lexical-exception windows, not the same-UID or crash-recovery residuals above.

The same audit found that a non-UTF-8 file credential registered no masking or
detection forms because its text value was intentionally empty. Bindings now
derive immutable forms once: their exact base64 is masked and lower/uppercase
hex is reported for binary values at least eight bytes long, while empty text
still cannot cause a phantom literal warning. The floor prevents ordinary words
such as `dead` from falsely proving disclosure of a two-byte file; shorter binary
values have no byte-derived base64/hex protection; valid UTF-8 content may still
retain text-derived forms. One opaque prepared-file object owns a defensive byte
snapshot and its forms, and repeated lexical bindings cannot separate or mutate
that pair. `SecretBinding` retains no additional byte array. Neither the owned
bytes nor derived managed strings are memory-zeroized. Regressions pin the
threshold, sharing, semantic boundaries, and caller-array independence.
