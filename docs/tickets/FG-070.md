# FG-070 — Secret delivery: value bound as Jenkins binds it, plus a file companion

**Status:** **DONE (re-scoped)**  ·  **Priority:** P0

Archived from the execution board on 2026-08-02. The board carries the
outcome; this file carries the reasoning, which is what a future reader
needs and what a planning table cannot hold.

---

**Measured first:** a secret in the environment is readable from `/proc/<pid>/environ` by any process running as the same user, for the whole life of the step — which is what `withCredentials` does. Fogell writes the value to a **0600 file** and the environment carries only `<VAR>_FILE`. A test prints the child's own environ and asserts the value is absent. **CLAIM CORRECTED** after a Codex review on PR #11, which was right: this does **not** defeat the same-UID attacker the measurement identified. That process reads `<VAR>_FILE` from `/proc/<pid>/environ` and then simply opens the 0600 file, because it owns it too. What FG-070 actually buys: the secret is gone from the environment, so anything that dumps or logs `environ` (crash handlers, `ps e`, process explorers, child processes started before the binding) no longer captures it, and a **different**-UID reader is blocked. Protecting a secret from a same-UID process is not achievable on Linux without UID separation or namespaces — see FG-070b. **CORRECTED A SECOND TIME** by the FG-044 measurement: Jenkins' `withCredentials` binds the VALUE (`env \| grep -c '^TOKEN='` is 1, `${#TOKEN}` is the secret's length) and every real pipeline reads `$TOKEN`, so binding only a path breaks lift-and-shift for all 23 corpus files that use credentials. Fogell now binds the value for parity AND the `_FILE` companion; `Secrets.environmentForPathOnly` keeps the hardened form for a caller that accepts the incompatibility. What protects the value is **masking on every output path** (FG-071), not absence from the environment
