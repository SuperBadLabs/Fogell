# FG-235 — Multiline credentials cross the progressive-output mask boundary

Priority: **P0**

Status: **DONE**. The bounded fail-closed implementation, regression tests,
compiling-mutant proof, exact-head gates, formal reviews, publication, and
source merge are complete. FG-236 owns the explicitly separate raw-stream
separator-insertion gap.

## What was reproduced

Fogell accepted arbitrary UTF-8 secret text and valid-UTF-8 file credentials,
including values containing CR or LF. `ProcessGroup.run` publishes stdout and
stderr through .NET's line callbacks. Those callbacks remove the physical line
terminator before `Executor.runShell` and `WalkerCtx` apply `Secrets.mask` to
each line.

For `TOKEN=alpha\nbeta`, `printf '%s' "$TOKEN"` published `alpha` and `beta`
as progressive controller-log lines. Neither line contained the registered
whole form `alpha\nbeta`, so both were emitted unmasked and without FG-071's
leak warning. The later buffered pass replaced the whole value with `****`, but
could not recall the already-published bytes. A UTF-8 file credential printed
with `cat "$CERT"` had the same failure. A value ending a fragment with CR was
worse: line framing removed the CR, so the fragment survived both progressive
and buffered masking.

This contradicted the current-tree threat model and FG-071 board claim that
registered literal forms are masked on streaming and buffered output. It was a
live confidentiality defect under a green build, not a missing compatibility
feature.

## Bounded correction

Until masking happens on the raw stdout/stderr streams, before line framing,
Fogell rejects a selected literal credential whose protectable UTF-8 text
contains CR or LF:

- secret-text values are checked before `Secrets.bind` creates a companion;
- both username and password components are checked before either sibling is
  bound;
- valid-UTF-8 file content is checked before its lazy masking forms or file are
  materialized; and
- direct `Fogell.Execution` binding entry points carry the same fail-closed
  backstop.

The runtime emits the stable non-secret code
`unsupported_multiline_credential`, names the credential id and component, and
does not run the wrapper body or its successor. A mixed safe/unsafe request is
preflighted as one unit in either order, so no safe sibling file is briefly
created before refusal.

The check is selection-scoped. An unused multiline store entry does not block a
build. An opaque invalid-UTF-8 binary file containing raw CR/LF bytes remains
admitted because it has no registered literal text form; its existing
unbroken exact-base64 masking boundary is unchanged. It does not imply that a
separator-inserting transform of that form is protected; FG-236 records the
independently reproduced wrapped-base64 gap. Ordinary single-line text,
username/password, and file credentials remain controls for this literal-value
boundary.

## Proof

The focused suites cover:

- direct LF and CR text-binding refusal with zero filesystem effects;
- UTF-8 multiline file refusal without forcing its lazy full-file forms;
- all five runtime components (text LF, text CR, username, password, file),
  each beside a safe sibling in both sibling orders;
- non-secret diagnostics, no masking narration, no wrapper/successor effects,
  and no `_secrets` materialization; and
- unused-multiline and selected opaque-binary controls.

`scripts/prove-fg235-multiline-secrets.sh` first runs the real tests, then builds
and kills two semantic mutants: one disables the shared CR/LF predicate, and
one bypasses only the normal runtime preflight so the direct binding backstop
throws outside the expected trace. A compile failure is not accepted as a
killed mutant. The proof is blocking in the build lane.

## Compatibility boundary and successor

This is intentionally a compatibility narrowing. Jenkins can store multiline
secret text and PEM-style file credentials; Fogell now refuses those selected
values rather than leaking them. Do not describe FG-235 as multiline credential
support.

Compatibility restoration requires source-aware streaming redaction before
physical-line parsing: independent stdout/stderr state, bounded longest-pattern
overlap, and an EOF flush that preserves output order. Splitting a secret into
line fragments is not an equivalent fix: it masks common fragments without
proving adjacency and still cannot reconstruct CR versus LF versus CRLF after
the callback has discarded the terminator.

Independent review reproduced a related but distinct failure after this
bounded correction: both a 90-character single-line text credential and a
90-byte opaque invalid-UTF-8 file have 120-character registered base64 forms;
GNU `base64` emits each as 76- and 44-character physical lines, both streamed
and buffered verbatim without a warning, while `base64 -w0` is masked. FG-236
owns that separator-inserting-transform class and the raw-stream redesign. This
disclosure is part of FG-235's closure: the literal-value fix must not be
mistaken for a general line-framing repair.
