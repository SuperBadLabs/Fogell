# `agent { docker }` and `agent { dockerfile }` on the same host through rootless podman, image digest pinned on both engines

Priority: **P1**

Verb: **run** a stage inside a container.

Status: **TODO**. Filed 2026-09-10 by the Track 4 re-cut; the containment
decision is recorded in `adr/0009`. Depends on FG-272.

## Demand

The `agent { docker }` and `agent { dockerfile }` rows of [FG-263](FG-263.md)'s
table (FG-050's wider 2026-08-17 pattern read 13 for `docker`). Both are
refused today, and the
parser discards the `dockerfile` body and the `docker` `args` field entirely
(2026-09-10 code read of `src/Fogell.Pipeline.Parser/Parser.fs`), so the first
step is to keep what the file says.

## Design

- Parser keeps `args`, `filename`, `dir`, `additionalBuildArgs`, `reuseNode`.
  `registryUrl`, `registryCredentialsId` and `customWorkspace` refuse by name.
- `Executor.StepRequest` gains `Launcher: HostLauncher | ContainerLauncher of containerId`;
  `ProcessGroup.run` execs `podman exec -w <cwd> -e … <id> sh -c <script>` for
  the container case. Jenkins' observable contract to match: `docker run -t -d
  -u uid:gid -w $WORKSPACE -v $WORKSPACE:$WORKSPACE:rw,z … <image> cat`, the
  workspace mounted at the same path. `args` is Jenkinsfile-controlled and
  therefore untrusted (Codex, PR #446): it is tokenised as Jenkins tokenises
  it and then checked against a strict ALLOWLIST before the command is
  composed — `-e`/`--env NAME=VALUE`, `-u`/`--user`, `-w`/`--workdir` under
  the workspace, `--entrypoint`, and `-v` ONLY for a source inside the
  workspace mapped to a target inside the container; anything else (host
  paths, `--privileged`, `--network`, `--cap-add`, `--device`, `--pid`,
  `--security-opt`, `--mount`, a quoted or unbalanced token) refuses by name
  (`unsupported_docker_args`) before any container exists. The composed
  command is tested against a fixture of containment-breaking flags and the
  test is proven to fail by planting one.
- Container lifecycle is an effect the journal must know, and the intent is
  recorded BEFORE the container exists: the name is deterministic,
  `fogell-<attempt>-<fence>`, the journal writes `ContainerIntent of name`
  and fsyncs before `podman run --name <name> --label fogell.attempt=<attempt>
  --label fogell.fence=<fence>`, then `ContainerStarted of id` after, and
  `ContainerRemoved` on exit. A resumed or reconciled attempt removes by name,
  which covers a SIGKILL between `run` and `ContainerStarted`; and a
  startup scavenger removes every container carrying a `fogell.attempt` label
  whose attempt is not under a live lease with that fence, which covers a
  SIGKILL before the intent record reached disk (Codex, PR #446). Timeout and abort `podman kill` then
  `rm -f` after grace — a second containment mechanism beside process groups,
  as `adr/0009` states.
- Under the fence: `--network=none`, the image pre-loaded on both engines with
  a pinned digest recorded in the receipt's comparison contract (FG-254's
  toolchain-pin discipline applied to an image). Rootless podman already runs
  `jenkins-lab` (FG-244), so the runtime exists on HeMan.

## Acceptance

A tier-1 receipt for a corpus file with `agent { docker { image } }` under the
fence with the image digest pinned on both engines; crash-lane cases proving
the container is removed after SIGKILL of Run.Host at three points (before the
intent record is durable, between `run` and `ContainerStarted`, and mid-step)
and again after a timeout inside the container; a `dockerfile` case proving
the build context is the declared directory.

## Jenkins probe first

Measure on luigi: the exact `docker run` line Jenkins prints (it is compared),
the `docker inspect` narration, the workspace path inside the container, the
uid it runs as, and what happens to `sh` output ordering through `docker exec`.
