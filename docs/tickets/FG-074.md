## Implemented contract

`Directory.Build.props` enables both `RestorePackagesWithLockFile` and
`RestoreLockedMode` for the repository. Each of the 26 project files declared by
`Fogell.slnx` has one adjacent schema-version-1 `packages.lock.json`. NuGet must
therefore resolve the checked-in graph in ordinary builds; a changed direct or
transitive graph requires an explicit, reviewed lock regeneration rather than a
silent floating update.

`scripts/prove-dependency-locks.sh` is wired at the start of
`scripts/build-and-test.sh`. It establishes the following bounded properties:

1. Inside a Git worktree, a repo-wide scan enumerates tracked plus untracked
   F#, C#, and Visual Basic project files and adjacent locks, applying the
   repository's per-directory `.gitignore` rules and explicitly excluding
   `.claude/worktrees/**`. Operator-global ignores and `.git/info/exclude` do
   not participate, so local configuration cannot hide a project or lock. In a
   source export without Git metadata, the fallback filesystem scan prunes only
   its enumerated non-source trees: `.git`, `bin`, `obj`, `.forge-home`,
   `.fogell-home`, and generated `evidence/*/workspace` trees. The resulting
   inventory must exactly match both `Fogell.slnx` and the adjacent lock-file
   inventory. Two projects in one directory are refused because they would
   share NuGet's default lock-file path.
2. MSBuild evaluates `RestorePackagesWithLockFile=true` and
   `RestoreLockedMode=true` separately for every discovered project. Checking
   only the repository default is insufficient because a project-local
   override can weaken it.
3. A newly created isolated NuGet package cache is proven empty, then populated
   by a network-enabled `--locked-mode --force --no-http-cache` solution
   restore. The proof refuses if that cache remains empty.
4. In a scratch copy containing the project graph and checked-in locks, a
   source-cleared `--force-evaluate` restore regenerates the graphs. Every
   regenerated lock must be byte-identical to its checked-in counterpart. This
   catches dependency-edge drift that ordinary locked restore does not
   necessarily diagnose from a hand-edited edge alone.
5. With NuGet package sources cleared, the real solution is restored in locked
   mode from the populated isolated cache. Hashes of all 26 checked-in locks
   must remain unchanged.
6. A Release `--no-restore` solution build uses that exact isolated package
   cache. The repository's existing FS0025 and FS0026 warnings-as-errors policy
   remains active.

The scratch directory, cleared-source configuration, fixtures, logs, and
isolated package cache are removed when the lane exits. Later gate consumers use
the Release outputs; consumers that issue their own ordinary `dotnet build`
retain their existing network-enabled restore behavior and are not part of an
offline claim.

## Proof of the proof

Seven independent planted states must be rejected:

1. **locked-mode override** — the non-first fixture project evaluates
   `RestoreLockedMode=false`;
2. **lock-file-policy override** — that non-first project evaluates
   `RestorePackagesWithLockFile=false`;
3. **solution inventory drift** — a project in a repo-wide `extras/` path is
   present on disk but omitted from `Fogell.slnx`;
4. **missing lock** — one adjacent project lock is removed;
5. **PackageReference drift** — a direct Npgsql version changes while its lock
   remains fixed, and locked restore must report NU1004;
6. **content-hash tampering** — a locked package hash changes, and restore must
   report NU1403; and
7. **dependency-edge tampering** — a transitive dependency edge changes while
   the other locked fields remain plausible, and regenerated-lock comparison
   must differ.

The first two mutations make the per-project, per-property policy loop
load-bearing. The third makes the repo-wide scan load-bearing rather than
allowing the proof to consider only the conventional `src/`, `tests/`, and
`tools/` roots. The final four separately exercise inventory, direct graph,
package-content, and transitive-edge enforcement.

A separate positive control initializes a scratch Git worktree whose
`.gitignore` excludes `.claude/worktrees/`, plants a complete nested project and
lock there, and configures a hostile operator-global ignore that would hide a
real solution project. Both inventory checks must still pass: the nested
worktree stays outside the repository inventory while the global ignore cannot
remove the real project or lock. This control makes both sides of the Git-aware
boundary load-bearing; it is not an eighth rejected mutation.

## SDK and regeneration boundary

`global.json` names SDK `10.0.301` with `rollForward: disable`, and the hosted
gate installs that exact version from the same file. The F# SDK supplies an
implicit direct `FSharp.Core` package; the current locks record `10.1.301`.
SDK and lock graph are therefore one reviewed unit: changing the SDK requires
intentional lock regeneration and review rather than allowing an installed or
newly released feature band to rewrite the implicit request.

The locks detect SDK/package-graph drift, while the exact SDK selection keeps
local and hosted locked restore on the graph that was reviewed. This still is
not a byte-for-byte reproducible-build claim: the SDK pin does not fix the OS,
native dependencies, environment, or every other build input.

## Non-claims and residuals

- The isolated cache is populated by a network-enabled restore. Clearing NuGet
  package sources for the later restore is not OS network isolation, does not
  block arbitrary process egress, and is not an airgap proof.
- The lane proves one source-cleared warm-cache restore and no-restore build. It
  does not prove the whole build-and-test gate runs offline, that an initially
  cold machine can build without fetching packages, or that later ordinary
  `dotnet build` consumers avoid the network.
- `--no-http-cache` prevents the proof from borrowing NuGet's HTTP response
  cache; it is not a claim that the isolated global-packages cache is
  independently trusted or attested.
- Lock-file content hashes let NuGet reject mismatched package content. They do
  not prove publisher identity, package safety, feed integrity, SDK integrity,
  or the absence of malicious content in a correctly hashed package/cache.
- Source-cleared restore cannot establish current advisory information. The
  lane explicitly makes no vulnerability-freshness or vulnerability-free
  claim.
- This slice does not emit an SBOM, sign artifacts, attest provenance, pin the
  OS or native toolchain, or make a reproducible-package claim. Those require
  separate release controls.
