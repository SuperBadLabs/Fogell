# FG-234 — A two- or three-space line inserted inside a bound RECOVERED block is accepted and unbound

Status: **TODO** (P3). Filed 2026-09-02 from the FG-128 pre-push verifier's
round-6 disclosure on the FG-128 head (PR #316).

## What was reproduced

Against the FG-128 head, in a scratch clone: bind `when-conditions.receipt.txt`
with the seal proof's own `bind_recovered` recipe (the block, its entry and a
correct `recovered-seal:` line), then insert a line indented by THREE spaces —
`   attempt 0: PROVEN (tier 1) — forged three-space narration line` — inside
the block, between the heading and the blank line that ends it.
`--verify-seals` on that directory returned `1 receipt(s) recomputed from their
own content, all match`, exit 0. A two-space line does the same.

## Why

Two rules in `src/Fogell.Differential/Compare.fs` disagree about what a block
line is. The accountability pass (the FG-161 "every line is either sealed or
declared unsealed" walk) treats the RECOVERED region as declared-unsealed and
admits ANY line starting with two spaces there; the FG-128 provenance hash
extracts only lines starting with FOUR spaces as entries. A line with two or
three spaces of indentation is therefore admitted by the first rule and
invisible to the second: it reads as narration to a human — the block's fixed
narration lines are two-space-indented — and is bound by nothing.

The `RecoveredFrom` doc comment in `src/Fogell.Differential/Compare.fs`
already says this in words ("the block's fixed narration and its position are
not hashed"); the rendered contract prose names only what IS bound (this seal
and the entries). So it is a disclosed limit, not a false claim. It
is filed because the gap is wider than "narration": a forged line can carry
an attempt-shaped sentence.

## What would close it

Either bind the whole region (hash the `RECOVERED:` heading itself and every
line after it up to the blank line, narration included — the heading's
visible "DIVERGED ... did not reproduce" claim is narration too, and a hash
that starts below it would leave that sentence editable; the narration is
fixed text, so this costs nothing in churn, and the FG-119 property is
untouched because the content seal is not involved), or refuse any line in
the region, heading included, that is neither one of the fixed narration
lines nor a four-space entry. The first is
simpler and closes the narration limit with it; the second keeps the "entries
are the bound thing" reading of the receipt. Neither binds the block's
POSITION: the verifier finds the block by searching for its heading, so an
unchanged heading and body moved elsewhere in the receipt hash the same
(Codex, on the filing PR). Position closes only if the verifier also demands
the canonical location — the renderer emits the block immediately before
`VERDICT:` — and that is a separate, optional step of this ticket. Either
way: a test that inserts the three-space line and expects a provenance
verdict, a proof arm beside 14.6, and the mutant that reverts the rule
failing exactly those two.

## Not this ticket

The round-6 verifier also noted that any (block, line) pair consistent over
the same content seal is indistinguishable from a genuine one, because the
recipe is a keyless sha256 — restoring an old genuine pair from git history,
or fabricating one with the public recipe, is invisible. That is the same
class as recomputing the content seal after editing an output line and is
outside what `--verify-seals` has ever claimed to catch; the seal is
tamper-EVIDENCE for accidental and casual edits, not a signature.
