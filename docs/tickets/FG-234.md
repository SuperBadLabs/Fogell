# FG-234 — A two- or three-space line inserted inside a bound RECOVERED block is accepted and unbound

Status: **PARTIAL — implementation, tests and proof arms are complete and
proven to fail under two reverting mutants; exact-head hosted gate and review
coverage are outstanding** (P3). Filed 2026-09-02 from the FG-128 pre-push
verifier's round-6 disclosure on the FG-128 head (PR #316).

## What was reproduced

Against the FG-128 head, in a scratch clone: bind `when-conditions.receipt.txt`
with the seal proof's own `bind_recovered` recipe (the block, its entry and a
correct `recovered-seal:` line), then insert a line indented by THREE spaces —
`   attempt 0: PROVEN (tier 1) — forged three-space narration line` — inside
the block, between the heading and the blank line that ends it.
`--verify-seals` on that directory returned `1 receipt(s) recomputed from their
own content, all match`, exit 0. A two-space line does the same.

## Why

Two rules in `src/Fogell.Differential/Compare.fs` disagree about what a block
line is. The accountability pass (the FG-161 "every line is either sealed or
declared unsealed" walk) treats the RECOVERED region as declared-unsealed and
admits ANY line starting with two spaces there; the FG-128 provenance hash
extracts only lines starting with FOUR spaces as entries. A line with two or
three spaces of indentation is therefore admitted by the first rule and
invisible to the second: it reads as narration to a human — the block's fixed
narration lines are two-space-indented — and is bound by nothing.

The `RecoveredFrom` doc comment in `src/Fogell.Differential/Compare.fs`
already says this in words ("the block's fixed narration and its position are
not hashed"); the rendered contract prose names only what IS bound (this seal
and the entries). So it is a disclosed limit, not a false claim. It
is filed because the gap is wider than "narration": a forged line can carry
an attempt-shaped sentence.

## What would close it

Either bind the whole region (hash the `RECOVERED:` heading itself and every
line after it up to the blank line, narration included — the heading's
visible "DIVERGED ... did not reproduce" claim is narration too, and a hash
that starts below it would leave that sentence editable; the narration is
fixed text, so this costs nothing in churn, and the FG-119 property is
untouched because the content seal is not involved), or refuse any line in
the region, heading included, that is neither one of the fixed narration
lines nor a four-space entry. The first is
simpler and closes the narration limit with it; the second keeps the "entries
are the bound thing" reading of the receipt. Neither binds the block's
POSITION: the verifier finds the block by searching for its heading, so an
unchanged heading and body moved elsewhere in the receipt hash the same
(Codex, on the filing PR). Position closes only if the verifier also demands
the canonical location — the renderer emits the block immediately before
`VERDICT:` — and that is a separate, optional step of this ticket. Either
way: a test that inserts the three-space line and expects a provenance
verdict, a proof arm beside 14.6, and the mutant that reverts the rule
failing exactly those two.

## Implemented boundary

The first option above, plus the optional position step, in
`src/Fogell.Differential/Compare.fs`:

- **One definition of the block's text.** `recoveredBlockLines` lists the
  heading, the two-space narration, the four-space entries and the NOTE lines
  exactly as `render` prints them; `render` iterates that list, so what is
  printed is what is hashed. The block's NOTE now says the whole block is
  bound (the previous wording named only the entries).
- **The hash covers the region.** `recoveredRegionSeal` is sha256 over
  `seal=<content seal>\nrecovered-lines=<N>\n` followed by every line of the
  region joined by `\n`, with a trailing CR canonicalised per line as before.
  The writer feeds it `recoveredBlockLines`; the verifier feeds it every line
  it reads back from the `RECOVERED:` heading to the blank line that ends the
  block, whatever the indentation. A two- or three-space line inserted
  anywhere in the region, an edited heading, or a dropped narration line is
  now a `ProvenanceMismatch`. The content seal is untouched, so a re-run proof
  still seals identically to its first attempt.
- **The position is bound.** After the region hash matches, the verifier
  requires the region to be followed by exactly one blank line and then the
  `VERDICT: ` line, which is where `render` puts it; otherwise it is
  `SealRefused` with a reason naming the position rule. The FG-128 refusals
  (block without line, line without block, duplicate block) are judged
  before position, so their wording is unchanged.
- **The accountability pass is unchanged in effect.** It still refuses an
  unindented line in the region; its comment now says that indentation is all
  it checks there, because every region line is bound by the hash.
- **Contract prose.** The two unsealed-region lists that every receipt prints
  now say the block is bound over the whole region and accepted only before
  the VERDICT line. The contract block is a declared-unsealed region, so the
  287 committed receipts — none of which carries a RECOVERED block — verify
  unchanged and are not regenerated; the prose regenerates with the next
  differential run, as it did for FG-128.

Tests, in `tests/Fogell.Differential.Tests` (`FG-234 recovered region
binding`, eight cases): the rendered region equals `recoveredBlockLines` line
for line and sits before the verdict; the ticket's three-space forgery and a
two-space forgery are each a provenance mismatch; an edited heading and a
deleted narration line are each a provenance mismatch; a block moved after
the engine sections and a second blank line before the verdict are each
refused by position; and a moved block with no binding line is still reported
as unbound, not misplaced. The ten FG-128 tests pass unchanged.

Proof arms, in `scripts/prove-seal-verification.sh` beside 14.6:
`bind_recovered` recomputes the new recipe by hand (over the block it plants,
not a value copied from the code under test); 14.7 plants the three-space line
from the reproduction above and 14.8 a two-space one, each refused as a
`PROVENANCE MISMATCH`; 14.9 cuts the bound block from before the verdict,
appends it after the engine sections and requires the position refusal by
name. Each arm guards that its plant landed before asserting.

## Proof of failure

Two mutants of `Compare.fs`, each applied to the source head, rebuilt in
Release, run through the 18 recovered-block tests (`--filter-test-list
recovered`) and the seal proof, then reverted; the clean tree was rebuilt
afterwards.

**M1 — the rule reverted on both sides.** The verifier hashes only the
region's four-space lines with their indentation stripped, and the writer
hashes only the entries: FG-128's recipe restored under the new label.

- Tests: 14 of 18 pass; exactly the four region cases fail — the three-space
  forgery, the two-space forgery, the edited heading and the deleted
  narration line. The position cases and the ten FG-128 cases pass, as they
  should: M1 does not touch position, and every FG-128 property holds under
  either recipe.
- Proof: arm 14.1 (a correctly bound block is ACCEPTED) fails, because the
  proof recomputes the FG-234 recipe by hand and the mutant no longer
  matches it, and 14.9 fails with the wrong reason (provenance mismatch
  instead of the position refusal) for the same cause. Arms 14.7 and 14.8
  PASS under M1 — vacuously, since a verifier that mismatches every bound
  block also mismatches the forged ones — and so, by the same mechanism, do
  the two older provenance-mismatch arms 14.2 (edited entry) and 14.6
  (transplant). Stated so the proof's kill is not over-read: on the proof
  side the accept arm is what detects a recipe regression, and a mismatch
  arm detects only a verifier that accepts genuine blocks and forged ones
  alike. The tests are the kill for the region rule itself.

**M2 — the position rule removed.** The refusal arm returns `SealValid`.

- Tests: 16 of 18 pass; exactly the two position cases fail — the moved
  block and the second blank line.
- Proof: exactly arm 14.9 fails ("the verifier ACCEPTED a tampered
  receipt"); every other arm, 14.7 and 14.8 included, passes.

No mutant was run against the accountability pass, which this ticket did
not change in effect.

## Acceptance

- The three-space reproduction above, replayed against this tree through the
  proof's own `bind_recovered` recipe, is refused as a provenance mismatch
  (arm 14.7), and so is the two-space variant (14.8) and a moved block (14.9).
- `dotnet run --project tests/Fogell.Differential.Tests -c Release --
  --filter-test-list recovered` passes 18/18 (ten FG-128, eight FG-234).
- `--verify-seals differential/receipts` reports all 287 committed receipts
  matching, so the new rule refuses no genuine receipt.
- The two reverting mutants fail the tests and arms named under *Proof of
  failure* and no others.
- The exact head passes the authoritative HeMan gate and the hosted gate and
  obtains Copilot and Codex coverage.

## Residuals and non-claims

- **Deleting block and line together is still invisible** to the verifier;
  a first-attempt-shaped receipt results and only git history sees it, as
  FG-128 stated.
- **The hash is keyless**, so a (block, line) pair fabricated with the public
  recipe over the same content seal is indistinguishable from a genuine one —
  the class named under *Not this ticket*, unchanged.
- **The narration is bound at render time, not to the current source.** A
  future edit to `recoveredBlockLines` changes the hash of receipts rendered
  after it; receipts rendered before it keep verifying against the text they
  carry. That is the no-churn property the ticket asked for, and it also means
  the verifier does not check that a block's narration is the CURRENT
  wording — only that it is the wording that was bound.
- **Only the differential receipt renderer and verifier changed.** The
  scorecard, the CLI's run-time RECOVERED reporting and the FG-119 retry are
  untouched.
- **Pre-existing and unchanged, found by the pre-push verifier while probing
  this change:** the ORDER of the header fields and the position of the
  `recovered-seal:` line itself are not bound (the block and the VERDICT
  paragraph moved together between `seal:` and `case-digest:` verify, and so
  does the binding line moved below the verdict) — the rule here is
  "immediately before the VERDICT line", not "in the renderer's header
  layout"; and a `RecoveredFrom` entry containing a newline renders a
  receipt that refuses itself in the accountability pass, loudly, under this
  recipe as under FG-128's.

## Not this ticket

The round-6 verifier also noted that any (block, line) pair consistent over
the same content seal is indistinguishable from a genuine one, because the
recipe is a keyless sha256 — restoring an old genuine pair from git history,
or fabricating one with the public recipe, is invisible. That is the same
class as recomputing the content seal after editing an output line and is
outside what `--verify-seals` has ever claimed to catch; the seal is
tamper-EVIDENCE for accidental and casual edits, not a signature.
