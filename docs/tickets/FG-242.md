## The instrument, validated before its numbers were read

FG-200 withdrew three survey attempts in a row because each instrument was
trusted before it had been run against a case whose answer was known. This
pass had exactly one such case — FG-200's own `cvitter_jenkins-pipeline-examples`
is `echo`-only and tier 1 — and the survey was accepted only after it
reproduced that answer and excluded the shapes that falsified the earlier
attempts:

1. Strip `/* */` block comments, then `//` line comments WITHOUT `DOTALL`
   (attempt 2's first run truncated every file at its first comment), then
   single-, double- and triple-quoted string literals, so text inside an
   `echo` argument cannot register as a step call.
2. Extract every identifier followed by `(`, `{`, or a bare argument, minus
   the declarative keywords (`pipeline`, `stages`, `steps`, `post`, …).
3. Flag any of: `sh`, `bat`, `powershell`, `pwsh`, `checkout`, `git`, `scm`,
   `library`/`@Library`, `withCredentials`, `credentials`, `docker`,
   `kubernetes`, `node`, `label`, `httpRequest`, `mail`, `emailext`,
   `slackSend`, `input`, `build`, `sleep`, `readFile`, `writeFile`,
   `archiveArtifacts`, `junit`, `stash`, `unstash`; and separately any file
   whose surviving call set contains an implicit-library global
   (`buildPlugin`, `buildPluginWithGradle`, `servicePipeline`,
   `packagePipeline`, `mavenPipeline`, `MPLPipeline`, `standardPipeline`,
   `goBuildViaGoReleaser`, `entry`, `evenOrOdd`; the survey's list also carried
   `getNumber`, which is `currentBuild.getNumber()`, a method rather than a
   global) or whose top
   level is a bare `identifier { }` call with no `pipeline` block
   (`simpleBuild { }`, and — as a BLIND SPOT the verifier found — every
   scripted `node { }` file, `bcgov_openshift-wiki` included). The blind spot
   was closed by a second scan with that rule removed: the only scripted file
   whose calls reduce to `node`/`echo`/`stage` plus more is
   `camiloribeiro_cdeasy`, and the more are `sh` and `parallel` (a step call
   in scripted form that the declarative-keyword strip hid). The echo-only
   answer is unchanged.

## What this measures that FG-200 could not

**The inert-surface pool is EXHAUSTED at 3 of 228.** FG-200 measured the
price of one receipt for an inert surface; this pass measured how many files
that price buys, and the answer is all three of them. Every remaining
admitted corpus file that is a pipeline (`HariSekhon_Templates` is admitted
and is a path line, so it bears nothing) carries at least one of these
FIVE, listed here as the capability each one waits on:

- a core step this engine has not modelled (`writeFile`) — and, in the same
  file,
- an `input` that needs an answer — exactly ONE admitted pipeline has these
  two as its only blockers: `executeautomation_JenkinsPipeline` (56 lines;
  four `echo`, one interpolating `${ChromeDriverPath}` from a trailing
  `environment { }`, `writeFile`, `input`, `archiveArtifacts`, two
  `parallel` blocks, one `when { branch 'master' }`). `archiveArtifacts`
  is receipted here; `writeFile` occurs nowhere in `src/`; and its `input`
  bars a receipt on its own — the differential harness has no approver on
  EITHER side (`WalkerOrchestration.fs`), so an answered prompt cannot be
  receipted, only a stopped one. The verifier found this file after the
  accounting draft repeated a three-class conclusion; the survey had
  dropped it because `input` sat in the flag list and in none of the
  conclusion's classes;

- `sh`/`bat`/`powershell` — waits on the no-egress fence being BUILT, per
  the operating contract and FG-200's probe that the fence does not exist;
- an implicit shared-library global — `buildPlugin` alone gates 58 files,
  the one survey figure that has survived every withdrawal;
- an SCM, credential or plugin step this lab cannot run.

So the fourth corpus receipt is not a selection problem. It is one of five
capability problems — the no-egress fence, implicit shared-library loading,
a modelled SCM/credential/plugin step the lab can also run, modelling a
core step (`writeFile`), or approval orchestration that answers an `input`
on both sides — and the fence is the cheapest per file because it is
infrastructure rather than engine work and unlocks files outright (next
section). Modelling `writeFile` is ordinary Wave 4 engine work, but it
would NOT make `executeautomation_JenkinsPipeline` receiptable on its own:
that file also needs the fifth, and the harness has no approver on either
side, so it is outside every current path (Codex on PR #380 caught the
draft calling it "the one candidate outside the fence's reach"; Codex on
PR #382 caught the same draft counting four classes while describing
five). A file
whose only blocker is an SCM, credential or plugin step is unlocked by none
of the others (Codex on PR #377 caught this conclusion naming only two; the
verifier on the accounting commit caught it naming only three).
