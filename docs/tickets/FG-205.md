# FG-205 — `sort` compares structurally, unrouted through the cycle-safe equality — a cyclic value in a sorted list still kills the process

Status: **PARTIAL — implemented, measured, receipted and tested in one
change; the exact-head hosted gate and review coverage are outstanding, and
the accounting commit that follows the merge flips this to DONE with the
head, merge and review identities** (P2). Raised by the pre-push verifier on the FG-191 landing (2026-08-17), from the
code, deliberately unmeasured: the row asked for a probe of `sort` over maps,
cyclic and acyclic, on both engines, "then the arm routed or refused to
match".

## The construction, as filed, and what had already moved

As filed: `List.sortWith compare` at the `sort` builtin was generic
structural comparison with no cycle guard, so `[m, m].sort()` on a
self-referential map recursed to a StackOverflow — the class FG-191 closed at
five sites, alive at a sixth.

That process-kill has been unreachable since 2026-08-21, when the FG-015b
review round (`a549f48d`, `b785e88b`, `f7ff114a`) gave the builtin
`Value.tryCompare`, a structural comparison that detects a revisited pair and
reports it as `OrderingCycleDetected`, and sealed `fg015b-cycle-sort-safety`
and `fg015b-sort-receiver-identity` (cyclic LISTS: the alias returns, two
distinct cycles throw a catchable Error). The row never moved, and the probe
it asked for — what Jenkins does with `sort` over MAPS at all — had not run.
Measured on 2026-09-03, two things were still wrong at `origin/main`
`a068258d`:

1. the cycle detector was PAIR-based: it stopped where the structural
   comparison stopped, so a pair whose elements differ before the cycle is
   reached (`[[1, m], [2]]` with `m` cyclic) returned normally here and
   overflows on Jenkins, whose `hashCode()` walks the whole element;
2. acyclic maps sorted structurally here, in an order Jenkins does not
   produce, and printed it.

Every "refused" cell is the one refusal, verbatim in the journal:

```text
unsupported_collection_ordering: Jenkins orders these elements by their Java hashCode (FG-205: measured for maps, lists and scalars of different classes), an order Fogell does not model; refusing instead of sorting them structurally
```

The rows are consistent with Groovy's `NumberAwareComparator` as its source
reads (unmeasured beyond the rows themselves): for a map, a list, or two
scalars of different classes (a String against an Integer, a Boolean against
an Integer) `DefaultTypeTransformation.compareTo` throws `Cannot compare`,
the comparator swallows that and orders by `hashCode()`. The measurement
alone establishes hash order: the printed 96 before 97 puts `[a:1]` before
`[a:0]`, 96 before 100 keeps `[a:1]` before `100`, and the computed `'ab'`
(3105) before `5000` and `1` before `true` (1231) fit and nothing else tried
does. Two UNEQUAL maps that tie on hash (`[b:2]` and `[a:1]`, both 96) come
out reversed from EITHER insertion order — what a comparison that is nonzero
and of the same sign in both argument orders produces under a sort's run
detection, an inference, not a printed value; three tied maps reverse the
same way. Where the tie is between EQUAL maps (`[[k: 1], [k: 1]]`) the order
stands.

The cyclic shapes, with `m`, `m1` and `m2` self-referential maps
`[k: 1, self: <itself>]`:

| shape | Jenkins | Fogell before | Fogell after |
|---|---|---|---|
| `[m, m].sort()` | returns | returns | returns |
| `[m1, m2].sort()` under `catch (Throwable)` | caught | caught | caught |
| the same under `catch (Error)` | caught | caught | caught |
| the same under `catch (Exception)` inside `catch (Throwable)` | escapes the inner, caught by the outer | same | same |
| `[[m], [m]].sort()` | caught | caught | caught |
| `[[1, m1], [2]].sort()` | caught | **returns** | caught |
| `[m1, 5].sort()` | caught | **returns** | caught |
| `[5, m1].sort()` | caught | **returns** | caught |
| `[[k: 1, self: null], m1].sort()` | caught | **returns** | caught |

The four bold cells are the first defect: Jenkins hashes both WHOLE elements
once the pair reaches the fallback, so a cycle anywhere inside either one
overflows, where Fogell's pair-based detector had already returned an order
from the first differing leaf (`1` against `2`, a map against an integer's
rank, a `null` against a map under the same key).

## What changed

`Value.tryCompare` in `src/Fogell.Groovy.Interpreter/Value.fs` is rewritten
to Jenkins' shape, and its doc comment says which shape that is:

- the same list or map object on both sides orders equal before anything
  else is inspected, so `[m, m].sort()` returns even when `m` is cyclic;
- `null` orders first; two integral numbers compare numerically; two strings
  by UTF-16 code unit; two booleans false-first;
- every other pair takes the hash fallback: `hasReferenceCycle` (FG-191's
  iterative scanner, now the one cycle authority for ordering) over either
  whole element reports `OrderingCycleDetected`, which the builtin raises as
  `CyclicValue Ordering` — catchable as Error and Throwable, not Exception,
  as before; an acyclic pair is `Unorderable`, and the builtin refuses by
  name with the text above.

The structural descent, its pair memo and its rank table are deleted; the
stale-reference audit then matched the deleted local `rank` against the
word in `Fogell.Domain/Status.fs`'s severity doc comment, which now says
"order" (a wording change, no code). The
refusal's wording moved (no receipt sealed the old text; the
`unsupported_collection_ordering:` name is unchanged).

Why refuse rather than route Java hash order, given that it is deterministic
and measured: three reasons, each a silent wrong order waiting to happen.

1. A tie between unequal elements is decided by an inconsistent comparison
   and the sort algorithm's run detection; reproducing it means reproducing
   JDK internals for every input length, not a rule.
2. By Groovy's source (unmeasured here) a GString hashes as
   `37 + toString().hashCode()` where a String hashes its code units, and
   `VStr` carries no such provenance — `[[a: "x${y}"], [a: 'q']]` would route
   to the wrong order with no way to notice.
3. `VInt` is "the wider, historically ambiguous integral surface": by Java's
   documented formulas an Integer and a Long holding the same negative value
   hash differently.

A routed order would be right by coincidence on the measured shapes and
wrong on the next; the refusal is loud and names the ticket.

Blast radius: `tryCompare` has one caller, the `sort` builtin — `min`,
`max` and `unique` were already refused as unknown methods (the FG-191 test
"every collection ordering entry point is host-safe"). One corpus file of
the pinned 228 calls `.sort(`: `gdemengin_pipeline-logparser.Jenkinsfile`
(lines 422–423) sorts a list of split strings, a same-class shape whose
order is unchanged. The three FG-015b sort receipts replay byte-identical
on this head through `Fogell.Run.Host`.

Tests: `FG-205 sort follows Jenkins' hash fallback boundary` (4): acyclic
maps and lists refuse by name; scalars of different classes refuse while
integral, string-with-null and boolean lists still order as measured; a
cyclic map anywhere in a hash-fallback pair (the four shapes above plus the
nested alias) is caught by Throwable and not by Exception; the identity alias
returns. Two FG-191 expectations for shared acyclic DAGs moved from a
structural `Order` to `Unorderable`; the cycle expectations beside them are
unchanged.

Proof of failure: with `Value.fs` at `origin/main` (`a068258d`) and this
head's tests compiled against it, exactly four of the 232 Fogell.Groovy tests
fail — the three FG-205 tests that assert a refusal or a fault (acyclic
maps and lists; scalars of different classes; a cyclic map anywhere in a
hash-fallback pair) and the FG-191 shared-DAG expectation — while the
identity-alias test passes on both trees, as the identity shortcut predates
this ticket. The fixed tree was restored and rebuilt afterwards (232/232).

## Residuals and non-claims

- Sorting acyclic maps, lists, or scalars of different classes is REFUSED
  where Jenkins succeeds. That is a fail-closed divergence by design; the
  three reasons above are the argument against ever routing it.
- `[[k: 1], [k: 1]].sort()` — equal content, distinct objects — returns on
  Jenkins (equal hash, `equals` true) and refuses here: the same refusal
  class, not a separate shape.
- `min()`, `max()` and `unique()` are untouched: refused as unknown methods
  before and after.
- A single-character string against a number (`['a', 1]`) is refused; the
  measured `[1, a]` is consistent with hash order (97) and with Groovy's
  source reading that a one-character String compares by its character
  code, and the measurement does not separate the two, so this stays
  refused.
- Two ranges as elements (`def r = 1..3; [r, r].sort()`) RETURNED
  (`Order 0`, a structural comparison of equal items) before this ticket and
  refuse now: a range value carries no reference for the identity shortcut,
  and the shape is unmeasured on Jenkins. `[[], []]` likewise returned and
  now refuses; `VFloat` pairs (reachable only through a JUnit duration,
  FG-214) are refused as before. Each is fail-closed, not measured.
- A decimal literal (`2.5`) is a parse refusal here, so the `[2.5, 1]` row
  is Jenkins-only; the parser reported that refusal at the enclosing
  statement's line and column rather than the literal's (noted, not filed).
- Jenkins' catch boundary is measured for `Throwable`, `Error` and
  `Exception` on the distinct-cycle shape only; the other cyclic shapes are
  measured under `Throwable`.
