# FG-200

**Step 1 of this ticket is a survey, and it has been run once — wrongly. The corrected
method is below and the number it produced is withdrawn.**

## What was asked

FG-200's acceptance asks how many of the 169 admitted corpus files have an executed surface
that is allowlistable at all. That number decides whether this ticket is a day or a quarter,
so it is worth getting before touching the lab.

## Survey attempt 1 — WITHDRAWN

Corpus verified 228/228 against the pinned manifest, then each of the 169 admitted files was
scanned for patterns that would stop it running against the oracle: SCM checkout,
credentials, network commands, agent labels, shared-library imports, triggers/parameters.

| blocker | admitted files containing it |
|---|---:|
| network (`curl`, `mvn`, `npm`, `docker pull`, …) | 39 |
| scm/git | 38 |
| agent label / docker / kubernetes | 19 |
| triggers or parameters | 15 |
| credentials | 13 |
| shared library (`@Library`, `library(`) | 11 |

It reported **89 of 169 with no blocker**, and that number is WRONG. Inspecting the shortest
"clean" files falsified it immediately:

- `jenkinsci_groovy-sandbox` and `awslabs_aws-codepipeline-plugin-for-jenkins` are
  `buildPlugin(useContainerAgent: true, configurations: [...])` — a global from the Jenkins
  plugin-pipeline shared library, loaded implicitly. No `@Library` line to match on.
- `bcgov_openshift-wiki` calls `openshiftBuild(bldCfg: ...)`, a plugin step.
- `HariSekhon_Templates` is the single line `jenkins/Jenkinsfile` — a path, not a pipeline.
  It is `admitted` because that text parses as a Groovy expression, which is a finding about
  what `admitted` means rather than about this file.

## Why it was wrong, and the corrected method

The scan asked **"does this file mention something hard?"** when the question is **"is every
step this file calls one that both engines can run?"** Shell-level greps cannot answer that:
the blocking construct is usually an ORDINARY-LOOKING CALL to a step that exists in Jenkins
via a plugin or an implicit library and does not exist in Fogell at all.

The corrected survey extracts every called step name per file and intersects it with the
steps Fogell actually registers, plus what `Sandbox.admitCall` admits. A file is a candidate
only if that intersection is total. That is a real measurement rather than a keyword count.
**NO BOUND IS CLAIMED FOR WHAT IT WILL REPORT.** A first draft of this paragraph said it would
come out "far below 89" — withdrawing a number and predicting its replacement in the same
breath is the same defect twice, and the second one is worse because it borrows the
credibility of the retraction.

**NOTHING SHOULD QUOTE THE 89.** It is kept here because the shape of the error is the useful
part: the first survey measured the surface it could see from outside the engine, and the
engine's own step registry is the only thing that answers the question.

## Survey attempt 2 — the corrected method, run 2026-08-15

Registry: `WalkerRules.scriptStepVocabulary` — `sh`, `echo`, `archiveArtifacts`, `junit`,
`checkout`, `deleteDir`, `git`, `stash`, `unstable`, `unstash`, `dir`, `timeout`, `retry`,
`withEnv`, plus `bat` and `script`. Sixteen names. Every call in each admitted file is
extracted and intersected with that set.

| filter | admitted files surviving |
|---|---:|
| every called step is modelled | **26** of 169 |
| …and no network / SCM / credentials use | **16** |

Smallest survivors: `griddynamics-archive_mpl` (2 lines), `jalogut_jenkinsfile-shared-library-sample` (5),
`stakater_GitWebhookProxy` (7), `cvitter_jenkins-pipeline-examples` (10).

**THE CAPABILITY BACKLOG, WHICH IS THE MORE USEFUL OUTPUT** — step names by how many admitted
files each disqualifies:

| files blocked | step |
|---:|---|
| 58 | `buildPlugin` |
| 14 | `buildDiscarder` |
| 14 | `logRotator` |
| 13 | `string` (a parameter/credential constructor) |
| 13 | `withCredentials` |
| 12 | `properties` |
| 10 | `disableConcurrentBuilds` |
| 9 | `timestamps` |

`buildPlugin` alone gates a third of the corpus. It is one global from the Jenkins
plugin-pipeline shared library, so the single highest-leverage capability here is not a step
at all — it is loading an implicit shared library.

**A FIRST RUN OF THIS SURVEY REPORTED 57 AND 46 AND WAS DISCARDED.** Its comment-stripping
regex was `//.*` compiled with `DOTALL`, so `.` matched newlines and every file was truncated
at its first line comment. Files that happened to comment early looked step-free and were
counted as candidates. The tell was `0 lines` in the output. Two surveys, two instruments
that were not validated before their numbers were read — the same defect the first attempt
was withdrawn for, in a different layer.

## Survey attempt 2 IS ALSO WITHDRAWN — review on PR #89

**26 and 16 and the backlog table are not measurements and must not be quoted.** Two
findings, both correct, and neither caught by me:

1. **The registry is misnamed and the wrong size.** `WalkerRules.scriptStepVocabulary` holds
   **14** entries. `bat` and `script` are NOT among them — I added both to my working set and
   then described the result as "`scriptStepVocabulary` — sixteen names". The counts were
   computed against a set that is not the one the table names.
2. **One registry was used where the repo has several.** `buildDiscarder`, `logRotator`,
   `disableConcurrentBuilds`, `timestamps`, `cron`, `pollSCM`, `string`, `booleanParam` and
   `choice` are DECLARATIVE `options` / `parameters` / `triggers` directives, not script
   steps. Classifying them against the script vocabulary conflates two languages.

The second has a sharp edge that shows how wrong the table is: **`timestamps` appears in the
backlog at 9 files, and FG-053 implemented `options { timestamps() }`.** The table lists as
missing a construct this engine already supports, so an unknown number of its rows are
inverted rather than merely imprecise.

**THIRD INSTRUMENT ERROR IN THREE ATTEMPTS AT ONE SURVEY** — keyword-matching in attempt 1,
DOTALL truncation in attempt 2's first run, the wrong registry in its second. The first two
were caught here; this one was caught by reviewers. The pattern is stable enough to state as
a rule: **for this ticket, no number is reportable until the instrument that produced it has
been run against a case whose answer is known independently.**

**WHAT SURVIVES BOTH OBJECTIONS**: `buildPlugin` gating 58 admitted files. It is a step call
under every registry in this repo, it is one global from an implicitly loaded shared library,
and no re-classification moves it. The highest-leverage capability for corpus coverage is
therefore still shared-library loading rather than any step.

**WHAT STEP 2 NOW NEEDS**, and the two PR #89 findings are its specification: re-run with
per-context registries — script vocabulary for `script { }` bodies, the declarative directive
tables for `options`, `parameters` and `triggers` — and recompute the backlog so
already-supported directives drop out.

## What 26 and 16 do NOT mean

Neither number says a file will RUN. They say its step names are modelled and, for 16, that
no obvious network, SCM or credential use appears. Behaviour is unproven, argument shapes are
unchecked, and `sh` bodies may still need tools this lab lacks. They bound the candidate pool
from above; the true count is discovered by taking one file end to end.
