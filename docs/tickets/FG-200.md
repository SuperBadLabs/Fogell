# FG-200

**Step 1 of this ticket is a survey, and it has been run once — wrongly. The corrected
method is below and the number it produced is withdrawn.**

## What was asked

FG-200's acceptance asks how many of the 169 admitted corpus files have an executed surface
that is allowlistable at all. That number decides whether this ticket is a day or a quarter,
so it is worth getting before touching the lab.

## Survey attempt 1 — WITHDRAWN

Corpus verified 228/228 against the pinned manifest, then each of the 169 admitted files was
scanned for patterns that would stop it running against the oracle: SCM checkout,
credentials, network commands, agent labels, shared-library imports, triggers/parameters.

| blocker | admitted files containing it |
|---|---:|
| network (`curl`, `mvn`, `npm`, `docker pull`, …) | 39 |
| scm/git | 38 |
| agent label / docker / kubernetes | 19 |
| triggers or parameters | 15 |
| credentials | 13 |
| shared library (`@Library`, `library(`) | 11 |

It reported **89 of 169 with no blocker**, and that number is WRONG. Inspecting the shortest
"clean" files falsified it immediately:

- `jenkinsci_groovy-sandbox` and `awslabs_aws-codepipeline-plugin-for-jenkins` are
  `buildPlugin(useContainerAgent: true, configurations: [...])` — a global from the Jenkins
  plugin-pipeline shared library, loaded implicitly. No `@Library` line to match on.
- `bcgov_openshift-wiki` calls `openshiftBuild(bldCfg: ...)`, a plugin step.
- `HariSekhon_Templates` is the single line `jenkins/Jenkinsfile` — a path, not a pipeline.
  It is `admitted` because that text parses as a Groovy expression, which is a finding about
  what `admitted` means rather than about this file.

## Why it was wrong, and the corrected method

The scan asked **"does this file mention something hard?"** when the question is **"is every
step this file calls one that both engines can run?"** Shell-level greps cannot answer that:
the blocking construct is usually an ORDINARY-LOOKING CALL to a step that exists in Jenkins
via a plugin or an implicit library and does not exist in Fogell at all.

The corrected survey extracts every called step name per file and intersects it with the
steps Fogell actually registers, plus what `Sandbox.admitCall` admits. A file is a candidate
only if that intersection is total. That is a real measurement rather than a keyword count,
and it will produce a number far below 89.

**NOTHING SHOULD QUOTE THE 89.** It is kept here because the shape of the error is the useful
part: the first survey measured the surface it could see from outside the engine, and the
engine's own step registry is the only thing that answers the question.
