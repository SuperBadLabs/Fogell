# FG-133 — A refusal cannot say WHY: unknown vs known-but-unimplemented vs wrong-scope are not distinguished

Status: **PARTIAL — implemented, measured, receipted and tested in one
change; the exact-head hosted gate and review coverage are outstanding, and
the accounting commit that follows the merge flips this to DONE with the
head, merge and review identities** (P3). Filed by FG-053(a)'s own review:
both refusal sites said only "does not support" because an earlier wording
claimed a split the code did not make — a pipeline `retry` (a name Jenkins
knows, unimplemented here) went out as "unknown", and a genuinely unknown
name in a stage block went out as "not honoured at stage scope".

## Implemented boundary

`src/Fogell.Differential/Fogell.fs`: beside the two refusal sites, the two
measured sets are carried as `jenkinsPipelineOptionNames` and
`jenkinsStageOptionNames`, and each refused name is worded by
`describePipelineOptionRefusal` / `describeStageOptionRefusal`:

- pipeline scope: `<name> (known to Jenkins at pipeline scope; not
  implemented by this engine)` or `<name> (unknown to Jenkins at either
  scope; Jenkins refuses it too)`;
- stage scope: `<name> (known to Jenkins at stage scope; not implemented by
  this engine at stage scope)`, `<name> (a pipeline-only option; Jenkins
  refuses it at stage scope too)`, or the unknown wording.

WHICH names are refused is unchanged: the descriptor table and the
stage-honoured set still decide that, and the Jenkins sets are consulted only
to word the refusal — conflating "Jenkins knows the name" with "this engine
implements it" is the FG-053 defect the table exists to prevent. Every
refusal is an `ERROR:`-class line, excluded from output comparison and
counted as the reported reason, so no existing receipt's compared content
moves.

Tests (`FG-133: an option refusal says WHY`, in the FG-129 refusal list;
Differential 351/351): the five shapes above through the walker with a
capturing output hook, asserting each refusal line verbatim, including the
fifth case — `ansiColor` at stage scope, which Jenkins accepts and this
engine honours only at pipeline scope.

## Closure

Receipts `compile-refusal-option-unknown-pipeline`,
`compile-refusal-option-unknown-stage` and
`compile-refusal-option-pipeline-only-at-stage` seal the three refusal
shapes tier-1 PROVEN (same pre-execution refusal, same result, same
workspace hash; output not compared, FG-129); 306 receipt seals verify
(303 before this change plus these three, after the rebase onto the FG-244
merge that added two corpus receipts) and the generated scorecard moves from
298 of 298 to 301 of 301 expected cases.
The pipeline-level `retry(2)` shape is deliberately not a case: Jenkins runs
it and this engine refuses it by name (FG-053(b)'s boundary), a divergence
by design.

## Residuals and non-claims

- The wording is a diagnostic, never compared by a receipt; the receipts
  seal that both engines refuse the three shapes before any effect.
- The Jenkins sets are this lab's plugin set; a name from a plugin the lab
  lacks reads "unknown to Jenkins at either scope" here and would be refused
  by this lab's Jenkins too, but might be accepted by another installation.
  The sets are constants beside the diagnostic, with the measurement date.
- `timestamps` at stage scope keeps FG-120's own refusal and wording.
- Pipeline-level `retry` remains refused (FG-053(b)); the new wording says
  that it is Jenkins-known and unimplemented here, which is the case the
  filing named.
