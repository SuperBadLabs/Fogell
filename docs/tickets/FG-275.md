# `build job:` bounded, same controller, through the effect ledger

Priority: **P2**

Verb: **trigger** a downstream job and **wait** for it.

Status: **TODO**. Filed 2026-09-10 by the Track 4 re-cut (`adr/0009`). Depends
on FG-266 (parameters) and FG-271 (a second executor). First runtime user of
`effect_checkpoints`, which the 2026-09-10 code read found has schema, Store
members and tests but no caller in the running controller.

## Demand

The `build job:` row of [FG-263](FG-263.md)'s table. A substring count of 179
for the word `build` was withdrawn on 2026-09-10 once the receiver split showed
`docker.build` and `buildPlugin` inside it. The row stays filed because it is
the first runtime consumer of the effect ledger, which is a durability
argument, not a demand one.

## Design

- Projects need a definition: a new migration (next free number at the time)
  `project_definitions`
  `(organization_id, project_id, revision, source_bytes, source_digest)` set
  through `PUT …/projects/{id}/definition`. `build job: 'slug'` resolves a slug
  in the same organisation; folder paths refuse.
- The step is one durability unit and goes THROUGH the closed dispatch path
  #424 landed, not around it: a `downstream` producer is registered in the
  `EffectProducer` registry and run by `EffectDispatch.runRegistered`, because
  `scripts/audit-effect-dispatch.sh` refuses any other caller of
  `PrepareEffect`/`AdvanceEffect` (Codex, PR #446). Run.Host emits
  `downstream.requested {key, project, parameters, wait, propagate}` on the
  existing event file; the producer's prepare/apply is `AdmitBuild` under the
  idempotency key `downstream:<parentAttempt>:<stage>:<stepIndex>:<occurrence>`,
  and the checkpoint reaches `applied` when the child is admitted. A resumed
  parent re-emits the same key and the dispatcher replays the checkpoint
  instead of admitting a second child.
- `confirmed` is NOT tied to the parent's lease, and that needs a schema rule,
  not only a different caller: #424's `fogell_guard_effect_checkpoint`
  trigger accepts a positive transition only while the checkpoint's parent
  attempt holds its original live lease, and terminal publication clears
  that lease, so a `wait: false` parent's checkpoint could never reach
  `confirmed` (Codex, PR #446). A new migration adds a `confirming_attempt_id`
  authority column and extends the guard: an `applied` checkpoint whose
  payload names a child build may be advanced to `confirmed` by the terminal
  publication of THAT child's attempt (matched on the child build id in the
  payload digest's source), inside the child's own transaction, with the
  parent's lease irrelevant. Any other cross-attempt transition stays
  refused. The reconciler applies the same rule for an `applied` checkpoint
  whose child is already terminal.
- Inbound result channel reuses the FG-046b approvals inbox mechanism verbatim
  (temp file plus atomic rename, newline-terminated, two stable polls), one
  file per transition so nothing is ever appended in place: the worker
  renames `<key>.scheduled` (`scheduled <number>`) into the inbox as soon as
  the child is admitted, and `<key>.terminal` (`terminal <status> <number>`)
  at the child's terminal publication. Run.Host's `build` arm returns on the
  `.scheduled` file for `wait: false` and on the `.terminal` file for
  `wait: true`; a partial file cannot be observed, and a crash mid-write
  leaves only the temp name, which the scavenger removes (Codex, PR #446).
- Bounds: a parent blocked in `build(wait: true)` holds an executor slot, so
  two such parents on two executors would wait on children that can never
  start, and counting parents that are ALREADY waiting still lets two be
  claimed before either waits (Codex, PR #446). So the reservation is taken
  at CLAIM time, inside `ClaimNextExecution`'s per-organisation advisory
  lock: a `build`-bearing definition (persisted at admission as
  `builds.bears_downstream boolean`) is offered only while the number of
  `build`-bearing attempts in a leased state is below `executors - 1`, so at
  most `executors - 1` potential waiters ever hold slots and one slot is
  always free for a child. Executors ≥ 2 is the floor, refused at admission
  as `downstream_needs_executor`; `ExplainWait` names the reservation when it
  is the reason a build waits. A
  child whose definition contains `build` refuses `downstream_depth_exceeded`
  (depth 1). Statement form only; using the return value stays refused by
  `StepValueUse`.
- Harness: `Jenkins.fs` creates one job per case today; multi-job cases need
  `cases/<name>/jobs/<slug>.Jenkinsfile` created before the parent runs. That
  extension is its own PR.

## Acceptance

A hand-written two-job case obtains a receipt for `build job:` with
`propagate: true` (child failure fails the parent step) and with
`wait: false` (the parent reaches terminal before the child does, and the
checkpoint is confirmed afterwards by the child's terminal publication);
`effect_checkpoints` holds exactly one `confirmed` row after a mid-step SIGKILL
of the parent and resume, and exactly one child build exists;
`scripts/audit-effect-dispatch.sh` passes with the new producer registered.
A tier-1 corpus receipt follows once FG-263 names a Declarative file whose
`build` is the step form.
